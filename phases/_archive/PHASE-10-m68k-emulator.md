# PHASE-10: m68k User Emulator

## Goal

Integrate the RuSTari m68k CPU core as a per-process emulation layer.
When `Pexec` loads a binary whose magic indicates m68k (`0x601A`), instead
of running it natively, instantiate an m68k emulator that interprets the
binary's instructions, intercepts `trap #1/#13/#14`, marshals arguments
across the m68k → AArch64 ABI boundary, and dispatches to the existing
TOS-API layer.

## Inputs

- `CLAUDE.md`, Phases 01–09 complete
- RuSTari m68k core (external, vendored as a workspace dependency)
- `docs/api/gemdos.md`, `bios.md`, `xbios.md` — every spec entry must
  have a complete **m68k ABI mapping** section (parameter stack layout,
  return register, side-effect register usage)
- Atari Compendium, "Calling Conventions" section
- MagiC PC architecture overview (Andreas Kromke's writings)

## Deliverables

### D1: RuSTari integration as a library
Vendor the RuSTari CPU core as `crates/rustari-cpu`. Strip out anything
that isn't the m68k execution engine — no Shifter, no MFP, no Atari memory
map. Expose a clean API:

```rust
pub struct M68kCore { /* … */ }
impl M68kCore {
    pub fn new(ram: &mut [u8], pc: u32, sp: u32) -> Self;
    pub fn step(&mut self) -> StepResult;
}

pub enum StepResult {
    Continued,
    TrapVector(u8),    // 1 = GEMDOS, 13 = BIOS, 14 = XBIOS, …
    Exception(M68kException),
    Halt,
}
```

The emulator runs **inside** a NewTOS process address space, with the
m68k "RAM" being a sub-region of the process's TPA.

### D2: m68k binary loader
Recognize TOS PRG with m68k magic `0x601A`, load text+data into the
emulator's RAM, apply m68k relocations, build the basepage at the start
of the RAM region per Compendium.

### D3: ABI marshaling layer
For each TOS API function, a marshaling shim:

```rust
fn m68k_gemdos_fopen(core: &mut M68kCore, args: &mut M68kArgs) -> i32 {
    // Read m68k stack-passed arguments (big-endian).
    let path_addr = args.pop_u32();      // m68k pointer into emulator RAM
    let mode      = args.pop_u16();
    // Translate emulator-RAM pointer to host pointer.
    let path = core.translate_str(path_addr);
    // Call native API.
    crate::tos_api::gemdos::fopen(path, mode)
    // Return value placed into D0 by caller.
}
```

The shim table is autogenerated where possible, hand-written where
parameter shapes are non-trivial (e.g., DTA pointers, basepage pointers).

### D4: Endianness handling for in/out structs
When a TOS call takes a pointer to a struct (e.g., `Fsetdta`), the struct
in m68k memory is big-endian. The marshaling layer either:
- (a) Byte-swaps fields on entry/exit at the API boundary, or
- (b) Provides accessor functions that always go through swap

Pick (a) for simple structs, (b) for structs the m68k program reads/writes
across multiple API calls (DTA falls in this category — the program's
`Fsfirst` writes it and the program's later code reads it). Document per
struct.

### D5: Exception handling
m68k exceptions (illegal instruction, address error, divide by zero) raised
inside emulated code do not crash the kernel. They terminate the m68k
process with a documented error code, exactly as a native crash terminates
a native process.

### D6: Performance baseline
Benchmark: the emulator runs at no less than the equivalent of a 16 MHz
68000 (i.e., faster than original ST). Measure with a known TOS PRG that
runs a synthetic loop. Record results in `docs/PERFORMANCE.md`.

If the interpreter falls below this threshold, **do not** start writing a
JIT in Phase 10. Document the gap and defer JIT to a follow-up phase.

## Exit criteria

- **EC1**: A trivial m68k PRG (compiled hello-world that calls `Cconws`)
  loads via `Pexec` and prints its message.
- **EC2**: Endianness is provably handled: a struct round-tripped between
  m68k and native code preserves values.
- **EC3**: An m68k illegal instruction terminates the process cleanly,
  kernel keeps running.
- **EC4**: Performance baseline met (≥ 16 MHz 68000 equivalent).
- **EC5**: ABI marshaling shim exists for every implemented TOS syscall.

## Out of scope

- m68k JIT (separate future phase)
- 68020/030/040 specific instructions (start with 68000, expand only as needed)
- FPU emulation (most TOS software doesn't use it)
- MMU emulation in the emulator itself (m68k programs in user mode don't
  touch it on real hardware)

## Risks

- **R1**: RuSTari may not be 100% accurate. Validate against a test
  suite (e.g., Mark Jenkin's m68k test ROMs, Hatari's regression tests).
- **R2**: Pointer translation. Every m68k pointer must go through
  `core.translate(addr)` to map to a host pointer. Forgetting once produces
  silent corruption. Wrap in a newtype `M68kPtr<T>` enforced by the type
  system.
- **R3**: Programs that hook traps via `Setexc` to install their own GEMDOS
  handler. Real TOS programs do this (TSRs, low-level utilities). NewTOS's
  `Setexc` is restricted (Phase 07 ADR); some programs will fail. Documented
  limitation.
- **R4**: Self-modifying code. The interpreter handles this naturally;
  any future JIT would not. Note this constraint.

## Claude Code instructions

- This is the most architecturally ambitious phase. Do not start coding
  until the m68k ABI mappings in all three TOS API spec files are reviewed
  and signed off.
- Resist the urge to make the emulator visible to the kernel-shared API
  layer. The TOS-API layer **does not know** that some callers are m68k.
  All m68k specifics live in the marshaling shim.
- Vendoring RuSTari: vendor a specific commit, document it, do not track
  upstream automatically. RuSTari is your own project elsewhere — but
  here it's a frozen dependency.
