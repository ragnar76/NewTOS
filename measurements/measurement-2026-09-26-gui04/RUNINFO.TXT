0. WHICH WHEEL IS REAL AND WHICH IS SYNTHESISED -- SAY IT PLAINLY
---------------------------------------------------------------------------
Runs A, B and C are on **raspi4b**, which has no USB host controller for us:

    [pcie] RC not present (no response at RC_BASE); USB disabled

so there is no mouse there, wheel or otherwise. Every wheel event in A/B/C is
a **synthesised USB boot-mouse report** handed to the very function the real
xHCI poll calls:

    crate::drivers::usb::hid::mouse_report(&[0,0,0,w,0,0,0,0], len)

with `w` = the wheel byte and `len` = the report length the Transfer Event
would give. That is one function short of the hardware: everything from
`mouse_report` down -- the byte-3 decode, the length guard, the IKBD
scancodes, `mousexvec`, `vdi_mousex_handler`, `call_user_wheel`, the EL0
upcall, `wheel_change`, `WM_ARROWED`, the desktop's scroll -- is the real
product code, unmodified.

Run D closes the remaining hop. It runs on **virt**, where QEMU gives us a
real emulated `usb-mouse` behind a real xHCI, and turns its wheel through
QMP: the report comes out of a genuine interrupt transfer. What is left for
the Pi is only whether a *physical* mouse behind the VL805 behaves the same.

The injectors and probes (method/apply_injector.py, method/gen_script.py,
method/usb_probe_patch.py, method/desk_arm_patch.py) are measurement
scaffolding: they are applied to an **rsync'd scratch copy** of the crates
(method/make_scratch.sh), never to the shared tree. Run D's kernel is the
shared tree plus the two `kprintln`s of usb_probe_patch.py; runs A/B/C's
kernels are the shared tree plus the injector.

2. RUN A -- the vex_wheelv chain            serial/run-a-wheelt.log
---------------------------------------------------------------------------
Script: method/wheel-a.actions -> wheel-a.rs. Eight synthesised reports:
+1, +1, -1, -1, -1, then one with byte 3 = 0x7f but `len == 3` (a mouse
WITHOUT a wheel), then +1, -1.

Result, verbatim:

    [WHL] 4 vex_wheelv installed, mine=0x00000000000013e4 old=0xffff000000115970
    [WHL] 5 wheel number=0 amount=-1 total=1
    [WHL] 5 wheel number=0 amount=-1 total=2
    [WHL] 5 wheel number=0 amount=1 total=3
    [WHL] 5 wheel number=0 amount=1 total=4
    [WHL] 5 wheel number=0 amount=1 total=5
    [h02] step 6 at +1300 ...                 <- the len==3 report: NO event
    [WHL] 5 wheel number=0 amount=-1 total=6
    [WHL] 5 wheel number=0 amount=1 total=7
    [WHL] 6 summary up=3 down=4 left=0 right=0 total=7
    [WHL] 7 vex_wheelv restored, got back=0x00000000000013e4

Three readings:

  * **The chain is served.** An EL0 application sitting on `vex_wheelv` sees
    the events -- byte 3 -> scancode 0x59/0x5a -> mousexvec ->
    vdi_mousex_handler -> call_user_wheel -> EL0 upcall -> its own routine,
    with wheel_number in the first argument and the signed detent count in
    the second (positive byte 3 = "up" = amount -1, EmuTOS
    vdi_mouse.c:546-547).
  * **7, not 8.** The sixth report carried byte 3 = 0x7f but a length of 3.
    It produced nothing, which is the report-length guard (FreeMiNT
    usb_mouse.c:255-261: "if there is a 4th byte, it must be z"). A mouse
    that sends only three bytes cannot make phantom detents.
  * **old = 0xffff000000115970** is a kernel high-half address: the AES's own
    wheel handler, installed at boot by our `gsx_init` equivalent
    (aes/gemgsxif.c:288-292). It also proves the LP64 pointer slot: gemlib
    reads `old` at CONTRL[11..14], not at EmuTOS' m68k CONTRL[9]. Before this
    change it was written at word 9 and an application read back rubbish.
    `got back=0x13e4` is the application's own routine coming back out of the
    restoring call.

5. RUN D -- a REAL emulated USB mouse       serial/run-d-virt-real-usb-mouse.log
---------------------------------------------------------------------------
The one run in which the report is NOT synthesised. QEMU's `virt` machine
carries the USB stack `tools/xtask` gives `--board qemu-virt`
(`-device qemu-xhci -device usb-kbd -device usb-mouse`) and our driver
enumerates the mouse for real:

    [usb] HID iface 0 protocol 2 -> int-IN ep 0x81 max 4 interval 7
    [usb] HID configured: slot 2 ep 0x81 dci 3 (mouse)

`max 4` is the point: QEMU's `usb-mouse` boot report is four bytes, the
fourth being the wheel. method/qmp_wheel.py turns that wheel with QMP
`input-send-event` (`wheel-up` / `wheel-down`), so the report comes out of a
genuine xHCI interrupt transfer. A serial probe on the two hops
(method/usb_probe_patch.py, scratch copy only) reports what arrived:

    3 x wheel-up:
      [gui04] report len=4 byte3=0x01
      [gui04] wheel -> scancode 0x59 x1
      [gui04] mousexvec(0x59)
      [gui04] mousexvec(0xd9)
    4 x wheel-down:
      [gui04] report len=4 byte3=0xff
      [gui04] wheel -> scancode 0x5a x1
      [gui04] mousexvec(0x5a)
      [gui04] mousexvec(0xda)

Three readings:

  * the transfer length really is **4**, so the guard of run A lets the byte
    through on a wheel mouse and blocks it on a three-byte one;
  * **positive byte 3 = up**: QEMU's `wheel-up` produces `0x01`, `wheel-down`
    produces `0xff` (= -1) -- an independent confirmation of the direction
    FreeMiNT's driver and the HID Usage Tables give;
  * the scancodes reach `mousexvec`, make and break.

Nothing else is changed in that tree: the two probes only print.

---------------------------------------------------------------------------
