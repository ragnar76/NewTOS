WHAT EACH LAYER CALLS (exactly)
  setup  Getbpb(3) once (D:'s BPB: recsiz, clsiz, datrec, numcl);
         Malloc(10 MiB + 64 KiB) read buffer; Fsetdta(own 44-byte DTA).
  L1     Lrwabs(0 /*read*/, buf, n, sector, 3 /*D:*/) -- logical BIOS read,
         no GEMDOS, no FAT, no sector cache. Contiguous range from D:'s first
         data sector (datrec, in 512-B units), byte size = file class
         (10 KiB, 100 KiB, 1 MiB, 10 MiB); once n=1 per call, once n=128 per
         call (last call shorter). Never a write. Reports ms, KB/s, ms/call.
  L2     per file D:\FSBENCH\<name>: Fsfirst(path,0) timed (DTA length checked
         against the manifest); then 4 rounds, each
           Fopen(path,0) | loop Fread(h, chunk, buf+total) | Fclose(h)
         with chunk = 512, 4096, 65536 and the whole file in ONE call; the
         loop stops at a short read or when total == size; each of the three
         calls timed separately; CRC-32 computed after the timed region.
  L3     per file: fopen(path,"rb") | loop fread(buf+total,1,1024,fp) until
         a short read | fclose -- default mintlib stdio buffering (BUFSIZ =
         st_blksize = 1024, the zView pattern); each timed; CRC-32 after.
  Pass 1 = cold (first after boot), pass 2 = warm: L1, L2, L3, then again.
  Nothing is printed while a region is timed except one progress line per
  step BETWEEN regions; C:\FSBENCH.LOG and C:\FSBNOKEY.FLG are touched only
  after both passes (C: shares the GEMDOS sector cache with D:).

CLOCK
  CNTVCT_EL0 is NOT usable at EL0: the kernel never writes CNTKCTL_EL1 (no
  hit for cntkctl in kernel/src), so EL0PCTEN/EL0VCTEN are not set by us
  (QEMU resets them to 0; real HW: architecturally UNKNOWN) -> an EL0 read
  would trap. FSBENCH therefore uses _hz_200 (0x4BA, 5 ms; the kernel credits
  ticks missed while a long SVC ran with IRQs masked, drivers/timer.rs
  handle_irq), refined: every timed region starts on a tick edge, and after
  it a spin loop counts to the next edge; elapsed =
  (t1 - t0 + 1) * 5 ms - spins_left / L * 5 ms, L = median of 9 calibrated
  ticks. The clock's own error bar is printed: 16 empty measurements
  ("empty measurement a..b ms"). In QEMU the spin rate varies by ~2x
  (295933..603561 spins/tick), so the empty measurement reaches 0.7..2.8 ms
  and sub-ms values (Fsfirst/Fopen/Fclose, also the 0.000 entries = clamped)
  mean nothing there. On the Pi the same line tells how far the sub-tick
  values can be trusted; values >= ~50 ms are tick-accurate either way.

OUTPUT
  Screen (Cconws), 4 pages <= 26 lines x <= 79 columns (QEMU console is
  80x30): 1 header + L1, 2 L2 cold, 3 L2 warm, 4 L3 cold+warm + summary.
  Between pages "-- photo, then press a key ... --" + Cconin; skipped
  (3 s pause instead, for screendumps) when C:\FSBNOKEY.FLG exists or argv[1]
  is "-n" -- the IKBD injector does not run during Cconin.
  C:\FSBENCH.LOG: the same 4 pages + "# L2 detail" lines (Fopen/Fread/Fclose
  of every round), appended. Header: Sversion, OSHEADER os_version/os_date,
  CPU clock (Ssystem 2000), D: BPB. The kernel build rev is NOT readable from
  EL0 (only on the boot screen) -> LIESMICH asks for a photo of it.
  Missing D: / missing files: reported (MISSING, fopen failed, Getbpb = 0),
  the run continues.

QEMU TIMINGS ARE NOT REPRESENTATIVE (QEMU models no card latency, its spin
rate jitters). Plausibility only, run3:
  L1 Rwabs ~4.3-4.8 MB/s, 1 vs 128 sectors per call about equal (no command
     latency in QEMU -- on the Pi this pair is THE number: CMD17 per sector).
  L2 10 MiB: 512 B 31-32 s / 4 KiB 7.9 s / 64 KiB 2.7 s / whole 2.3 s --
     the quadratic per-Fread chain walk of FS08 §2.2 (2 KiB clusters here).
  L3 10 MiB with 1 KiB fread: ~19.8 s (10241 freads).
