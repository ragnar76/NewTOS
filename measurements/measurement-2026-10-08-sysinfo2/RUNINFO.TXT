Esc -- OPEN, needs a kernel AES change (not made: ticket rule "kernel AES
  change required -> STOP and report")
  diag.actions (screendumps/diag-*, serial/diag-serial.log): Serial console
  drop-down open, Esc (IKBD 01/81) at 2800 and again at 3100: the box stays
  (X03/X04/X05); the next click beside it closes it (X06). Cause, from the
  code: while the accessory waits in its own evnt_multi it sleeps
  (sched::sleep), the scheduler runs the in-kernel EmuDESK (serial
  "[sched] switch -> kernel client"), whose evnt_multi(MU_KEYBD|...)
  (kernel/src/desk/main.rs:89) takes the key from the ONE global console ring
  (tos-api/src/aes/event.rs:556-560 console_try_read_key, first poller wins).
  EmuTOS hands a key only to the mouse owner -- kchange -> post_keybd(
  gl_mowner->p_cda, ch) (references/emutos/aes/geminput.c:288-307) -- which
  under wind_update(BEG_MCTRL) is the accessory. The kernel's own form_do /
  form_alert never sleep (busy loops, tos-api/src/aes/form.rs modal_loop /
  form_do), so Return there works; that is why the dialog's OK/Return and
  the alert's Return work. Same mechanism hits Return and the cursor keys
  inside the drop-down. The accessory code for them is in place (EmuTOS
  model); it works once keys follow the mouse owner. Not done: a polling
  workaround (evnt_multi with a 0 ms timer so the accessory never sleeps) --
  it would hide the kernel deviation and burn the CPU in an accessory.
