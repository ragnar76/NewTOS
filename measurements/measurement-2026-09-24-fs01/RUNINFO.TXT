  FS01 (Fdelete/Ddelete leave the long-name slots behind as orphans)
===========================================================================

Base: branch desk-rebuild, HEAD 07e55b4. The FS01 change is UNCOMMITTED in
the shared tree (tos-api/src/bdos/fs/{dir.rs,file.rs,dirops.rs} plus the new
host test tos-api/tests/gemdos_fs_lfn_delete.rs and the raw-image helpers in
tos-api/tests/fatvol/mod.rs). Nothing flashed, nothing ejected, no real Pi
run, nothing committed; no `git checkout/restore/clean/stash/reset` ran on
the shared tree. No git command touched it at all.

Machine: QEMU `-M raspi4b`, 640x480, `-display none`, serial to file, QMP
screendumps (`method/run.sh` + `method/qmp_multi.py`). Host: macOS,
`fsck_msdos` from the running system.

No `*.img` in this directory (the ticket's rule). Every image is rebuilt
from `method/seed.sh` and the two runs below.


1. THE CARD
---------------------------------------------------------------------------
`method/seed.sh` builds it with `tools/make-sd-image.sh` (64 MiB, MBR +
FAT16 -- the single source of truth for a NewTOS card) and adds a deliberate
long-name fixture on the root:

    C:\A very long file name.txt                 8.3 AVERYL~1.TXT + 2 LFN slots
    C:\A very long folder name\                  8.3 AVERYL~3     + 2 LFN slots
    C:\A very long folder name\inside long.txt   8.3 INSIDE~2.TXT + LFN chain

plus the long names macOS writes by itself (`.fseventsd`, `.Spotlight-V100`,
the `._*` companions) -- which is where the original finding's orphan slots
came from.

The freshly seeded card has 0 orphan long-name slots and passes
`fsck_msdos -n` phases 1/2/3 with rc=0 (serial/fsck.txt, first block).

Note on counting: `method/lfn_orphan_scan.py` counts an orphan only when the
`attrib == 0x0F` slot is still LIVE (first byte neither 0xE5 nor 0x00) and
its 8.3 entry is erased. The DESK24/25/26 probe counted by the 8.3 entry
alone, which on a make-sd-image card also counts ~30 ALREADY ERASED slots
(macOS deleting its own `._*` companions). Those are free slots and bother
nobody; the strict count is what fsck_msdos reacts to.

4. WHY A SINGLE ORPHAN ONLY WARNS AND THE EMPTIED CARD KILLS fsck_msdos
---------------------------------------------------------------------------
The open question from the DESK24/25/26 run. `method/abort_probe.sh` answers
it with twelve controlled cases on the SAME image (serial/fsck.txt):

  * It is NOT a count effect. Each of the five orphan chains ALONE, with the
    other seven slots freed by hand, kills fsck_msdos exactly as all eight
    do (cases "ONLY the chain at slot(s) ...").
  * Freeing all eight by hand makes the identical image pass (rc=0) -- the
    DESK24/25/26 counter-proof, reproduced.
  * One hand-made orphan on the still-LIVE card only warns:
    "Invalid long filename entry for /.Spotlight-V100", rc=206.
  * The difference is whether the orphaned chain is ever CLOSED by a live
    8.3 entry. Planting a single live entry AFTER the chain (immediately
    after it, or far away at the end of the directory) turns the crash into
    that same warning; planting one only BEFORE the chain does not.

So: fsck_msdos reports an invalid long-name chain at the moment it reaches
the next live short entry -- the warning even names THAT entry, not the
orphan. On a completely emptied card no live short entry follows any chain,
the scan reaches the end-of-directory marker with the chain still open, and
that path dies. That is a defect IN fsck_msdos (a tool must not trap on a
directory it can parse); the card's FAT is consistent and both copies agree.
It is not a second NewTOS defect, and NewTOS no longer produces the input.

The earlier run's "no output at all, not even the banner" was an artefact of
its `fsck_msdos ... | sed` pipeline: stdout is then a fully buffered pipe and
a process killed by a signal never flushes it. `method/fsck.sh` runs
fsck_msdos on a pty (`script`), which is why the two phase lines are visible
here.
