CAUSE (spec: docs/api/aes/event.md "Who gets a key -- the mouse owner (gl_mowner)", written first)
  tos-api/src/aes/event.rs evnt_multi's MU_KEYBD arm (and evnt_keybd) read the one IKBD key ring
  for whatever AES client was polling. With the cooperative kernel the SYSACC accessory sleeps in
  its drop-down's evnt_multi(MU_KEYBD|MU_BUTTON|MU_M1) under wind_update(BEG_MCTRL); the scheduler
  runs the in-kernel EmuDESK, whose evnt_multi(MU_KEYBD|...) took Esc/Return/the arrows.
  EmuTOS: gl_mowner is the "current mouse/keybd owner" (references/emutos/aes/geminput.c:52);
  chkkbd reads a key only for it (gemdisp.c:158-177), kchange -> post_keybd(gl_mowner->p_cda, ch)
  (geminput.c:288-308), a wait reads its own queue (gemevlib.c:173-182, akbin geminput.c:486-493).
  gl_mowner = top window owner via the Control Manager's w_setactive (gemwmlib.c:322-334,
  gemctrl.c:439-442), the caller under fm_own / BEG_MCTRL (gemfmlib.c:82-107), chkown on a press
  (geminput.c:310-335), ctl_pd on a hover into the bar (:388-389); hand-over only with the button
  up (set_mown :220-235) and outside a menu track (ct_chgown gemctrl.c:392-397). There is no
  gl_kowner in this EmuTOS: the keyboard owner IS gl_mowner. The application chain (desktop,
  launched program, Pexec children) is one AESPD (geminit.c:851-877), each accessory its own.

FIX (Rust; spec sections cited in the code)
  tos-api/src/aes/input.rs   GL_MOWNER_PD / GL_COWNER_PD: the AES identity the application half
                             of gl_mowner/gl_cowner names (next to the existing ctl_pd flag);
                             enum Mown (Ctl | Pd(identity)) for get_mown/set_mown/ct_chgown;
                             set_mown moves both identity halves (button-up guard unchanged);
                             bchange's chkown fills the identity (+1 gl_cowner, 0 desktop window
                             owner); w_setactive = top window's owner, but keeps the owner while
                             ml_ocnt > 0 (ctlmgr is dormant inside a BEG_MCTRL bracket: nothing it
                             waits for can fire); owns_keys(idx) = flag && same_pd(owner, idx);
                             same_pd folds every non-accessory identity into the chain.
  tos-api/src/aes/window.rs  ML_PMOWN carries an Mown (identity), fm_own's 0->1 edge gives the
                             mouse to the caller's identity; top_owner(), desk_owner() (unowned
                             desktop window = the chain), mctrl_held().
  tos-api/src/aes/acc.rs     is_process(idx).
  tos-api/src/aes/event.rs   evnt_multi MU_KEYBD and evnt_keybd take a key only when
                             owns_keys(caller); evnt_keybd runs the Control Manager's loop head
                             (w_setactive) per pass, as evnt_mouse already does.
  Named deviations (spec "Where NewTOS differs"): the key is assigned when read, not when forked
  (the ring is also the GEMDOS console's, and accessories keep running during a TOS program);
  keys typed while ctl_pd owns are not eaten but wait; w_setactive runs at every wait pass of
  every client (inline Control Manager) except under ml_ocnt > 0; the kernel's own modal loops
  (form_do/form_alert/fsel, busy loops that never yield) read the ring directly.

NOT DONE / OPEN
  - Real Pi 4 not run (workers take no HW actions). QEMU raspi4b has no USB: the input source
    is the scratch injector at the usb::poll sites; the USB-HID key path into the same ring is
    HW-only.
  - Keys typed while ctl_pd owns the mouse (button held on a frame, during a menu track) wait for
    the next owner instead of being eaten (named deviation, spec).
  - After an accessory's form_do/form_alert, EmuTOS leaves it the key owner until ctlmgr next
    loops; NewTOS hands the keys back at the next wait pass of any client (inline Control
    Manager timing, spec). Not observable in any run here.
  - The mouse-button/rectangle ownership test (own_mouse, "rlr == gl_mowner") is still the
    single-app flag; only keys follow the identity. Out of this ticket.
  - An accessory that tops its own window but waits without MU_KEYBD would leave typed keys in
    the ring (EmuTOS: they pile up in its queue); none of the shipped accessories has a window.
