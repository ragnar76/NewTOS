FINDING (out of scope, SDK; not changed): mintlib stdin does NOT reach Fread on
  NewTOS. sdk/libc/newtos-arch/isatty.c replaces mintlib/isatty.c and never sets
  __open_stat[].flags (stays 0), so __read (mintlib unix/read.c:72-74) takes the
  RAW path: _console_read_byte -> Fgetchar (EINVFN) -> Crawcin, no echo, no
  CRMOD; that path reads TWO keys per byte (unix/read.c:176 and :183, the first
  discarded -- upstream mintlib-0.60.1 code) and fgets never sees '\n'. With the
  flags upstream __isatty sets (CRMOD|ECHO, mintlib/isatty.c:55-57) the cooked
  TOS path runs over the new Fread line read and getchar/fgets work (part C).
  The spec note in 3f-fread.md ("getchar()/fgets() ... reaches Fread(0, ...)")
  therefore does not hold for the current SDK.

OBSERVABLE BEHAVIOUR CHANGES (all per spec)
  * Fwrite to AUX/PRN (-2/-3, std handles 2/3 by default, Fdup/Fforce to them)
    returns 0 and writes nothing (was: count, bytes on the console). A program
    writing to handle 2 without mintlib's Fforce(2,-1) loses that output, as on
    TOS/EmuTOS where handle 2 is the serial port.
  * Fread on AUX/PRN returns len NULs at once (was: blocking console read).
  * Fread on CON: len 1 echoes and stores the key (CR raw); len >= 2 is a line
    read ending at CR/LF (terminator not stored, echo CR) with BS/DEL/^X/^U/^R
    editing and ^C = Pterm(-32); HUGE / 32768..65535 -> 0 (was: blocking raw read
    of exactly len bytes, no echo).
  * Fwrite on CON: count <= 0 returns count (was 0); a pending ^C at the queue
    front ends the write with Pterm(-32) (was: no break check).
  * Midiws reads its buffer (an unreadable ptr is now a user-pointer fault).
