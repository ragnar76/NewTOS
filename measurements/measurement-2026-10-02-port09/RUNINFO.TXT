1. WHAT IS UNDER TEST
---------------------------------------------------------------------------
Precondition of the ticket's step 2: does the environment a launching EL0
program hands to Pexec (TeraDesk: startprg.c:543-567 builds it, :650-655
sets tail[0]=127, :312 x_exec(0, name, &cl, envp)) reach the child in a
form the child can read?

method/envpar.c is TeraDesk's single-task launch in miniature: Pexec(0,
child, tail, env), tail[0]=127 + the first 125 characters, env =
"PATH=C:\\0ARGV=\0<child>\0" + 14 arguments (196 chars joined; one with
blanks) + "\0". Children: method/envkid.c (prints p_env, then walks the env
block), and the existing C:\ARGVTEST.NAP (sdk/examples/argvtest.c).


2. RESULT: THE ENVIRONMENT DOES NOT REACH THE CHILD
---------------------------------------------------------------------------
serial/envkid.log:

  [EPAR] 2 calling Pexec(0, C:\ENVKID.NAP, tail[0]=127, env)
  [exec] preparing program (slot 3)
  [EKID] 1 p_env=0x000000000209b000 p_cmdlin[0]=0x000000000000007f
  [EKID] 2 reading the environment block at p_env
  [EXC] synchronous (non-SVC) exception (Data Abort (lower EL)):
        ESR=0x0000000092000006 ELR=0x00000000000010a4
  [EXC] FAR=0x000000000209b000

The first read of *p_env faults: ESR EC 0x24 (data abort from EL0), DFSC
0b000110 = translation fault level 2, FAR == p_env. The machine does not
come back (log ends there).

Cause, read off the source: the loader stamps the env block's POOL
PHYSICAL address into the child's BasePage --
  tos-api/src/bdos/process/loader.rs:502-507  env_phys = alloc_env_for(..)
  tos-api/src/bdos/process/loader.rs:675      bp.p_env = env_phys.unwrap_or(0)
  tos-api/src/bdos/process/loader.rs:1235ff   alloc_env: mxalloc -> phys
-- and never maps it into the child's EL0 space. The pool's PAs are mapped
only in the kernel high half (tos-api/src/bdos/process/usermem.rs:4-8 says
so in as many words); EL0 Malloc/Mxalloc blocks go through usermem::map
(ADR-021), the env block does not. 0x209b000 is above the 32 MiB EL0 range
(mmu.rs:80-87, USER_TPA_MAX_VA). The selftest that covers p_env
(kernel/src/selftest_pexec.rs:378-397) checks the block through the KERNEL
alias, which is why this was never seen.

Same for Pexec with env == NULL (EnvSpec::Inherit, exceptions.rs:1645-1647):
also a nonzero pool PA. Launches from our desktop / AUTO / boot launcher pass
EnvSpec::None (kernel/src/launch.rs:70-79), p_env = 0 -- those are fine.


3. STATUS QUO OF THE ARGUMENTS (for the record)
---------------------------------------------------------------------------
serial/argvtest.log, same parent launching C:\ARGVTEST.NAP: the libc
startup (cmdargs.c) reads the tail only. argc 12: alpha-one .. juliet-ten,
then "kilo-el" (the tail cut mid-word at 125 chars); kilo-eleven,
lima-twelve, "mike thirteen has blanks", november-... are lost. That is
what the ticket's acceptance would have to turn into argc 15 (argv[0] =
"C:\ARGVTEST.NAP" + 14), and it cannot while p_env is unreadable.


4. WHY NO LIBC CHANGE WAS MADE
---------------------------------------------------------------------------
An ARGV-aware __libc_parseargs must dereference p_env. Today every child
that TeraDesk launches gets a nonzero, unmapped p_env (PT_ARGV ->
explicit env; otherwise env NULL -> inherit), so the change would fault
every libc program started from TeraDesk at startup -- QED included --
exactly like ENVKID above. Per the brief: stop and report before touching
kernel/ or tos-api/.
