BEFUND ZUR VORHERSAGE DES ENTWURFS (§1.5 "[gefolgert]": TeraDesk loesche vor A57 13 Eintraege)
  WIDERLEGT durch die Messung: tera-before-B-view-menu.png == tera-after-B-view-menu.png (0 Pixel);
  die View-Tafel zeigt vorher wie nachher Show as icons / Auto arrange / -- / Sort by name / Sort by
  extension / Sort by date / Sort by size / View unsorted / Reverse order (MREVS) / -- / Show size
  (MSHSIZ) / Show date / Show time / Show attributes / -- / Set mask...; die File-Tafel vorher wie
  nachher mit Delete... (MDELETE), Copy disk... (MFCOPY) und ihren drei Trennern (SEP1-3). Grund
  (aus dem Quelltext): TeraDesk liest `buffer.size` als 8-Byte-`long` (LP64) aus einer Union, von
  der `wind_get` nur die unteren 4 Bytes (`words.high/low`) schreibt; die oberen 4 Bytes sind
  Stapelinhalt (resource.c:233-241,307-315) -- eine App-seitige LP64-Falle (T04), kein Kernthema.
  Vorher: untere 4 Bytes 0 (Dispatcher-Nullung, A27) + Stapel oben -> Vergleich fiel nicht auf
  Loeschen. Nachher: untere 4 Bytes 614400 -> ebenfalls kein Loeschen. TeraDesk sieht die Adresse
  jetzt (Trace), benutzt sie aber nach dem Quelltext nur fuer diesen Vergleich.
