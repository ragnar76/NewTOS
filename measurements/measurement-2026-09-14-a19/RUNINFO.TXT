A19 -- the AES dispatcher copies the input arrays once and clamps them.
Measurement, 2026-09-14.
MEASUREMENT ONLY: this directory states what ran and what came back.

WHAT CHANGED (the thing under test)
  tos-api/src/aes/mod.rs
      Aespb no longer hands the managers the caller's int_in / addr_in
      arrays.  `Aespb::from_raw` copies them ONCE into dispatch-local
      buffers and clamps while copying, which is EmuTOS' xif
      (aes/gemsuper.c:435-439):
          if (IN_LEN)  memcpy(int_in,  ..., min(IN_LEN,I_SIZE) *sizeof(WORD));
          if (AIN_LEN) memcpy(addr_in, ..., min(AIN_LEN,AI_SIZE)*sizeof(LONG));
      New constants I_SIZE = 16 (aesdefs.h:122) and AI_SIZE = 3
      (aesdefs.h:124) next to the existing O_SIZE = 7.  `dispatch` allocates
      `local_intin[I_SIZE]` and `local_addrin[AI_SIZE]` alongside the
      `local_intout[O_SIZE]` it already had, all zeroed for the same stated
      reason: EmuTOS' auto storage is indeterminate, so there is no value to
      reproduce, and a defined 0 is what a manager reading past the
      declaration now sees instead of application memory.
      `intin()`, `intin_ptr()` and `addrin()` read the local buffers; a new
      `caller_intin` field keeps the caller's pointer for the trap tracer
      alone (trace::flags::NO_INTIN), dead-code-gated off the aes-trace
      feature so the warning count does not move.
  tos-api/src/aes/trace.rs
      captures int_in / addr_in[0] from the dispatch-local buffers -- what
      the manager actually saw -- and reports NO_INTIN off `caller_intin`.
  tos-api/tests/aes_dispatch_inlen_clamp.rs   new, 5 tests.
  The OUTPUT side was ALREADY clamped before this ticket
  (`Aespb::copy_intout_back`, min(OUT_LEN, O_SIZE), and the managers already
  wrote a dispatch-local int_out).  Nothing was changed there.

WHAT THIS RUN DOES NOT COVER
  * Real Pi 4.  Nothing in this change is board-dependent -- it is pure
    parameter marshalling in tos-api, identical code on both boards -- but no
    hardware action was taken and no hardware run happened.
  * Interactive use.  QEMU raspi4b gives input or C: storage, not both.
  * An ILP32 caller.  Both the dumper and the host harness are LP64, so the
    `Abi::Ilp32` arm of the addr_in widening and of `intin_ptr` is exercised
    by neither.  It is the same arm as before the change -- `abi.read_ptr`
    moved from read time to copy time and nothing else -- but it is not
    measured here.
  * The aes-trace feature.  It compiles (checked, 64 warnings either way) and
    its two capture sites were moved to the local buffers, but no traced run
    was taken.
