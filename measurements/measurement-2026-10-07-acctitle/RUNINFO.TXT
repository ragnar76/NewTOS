RESULT IN ONE LINE
  Red reproduced in QEMU (same esr, same addr ffff000000193af0 on the HEAD
  release kernel, same pc text+0x489a4 / lr text+0x1cd64 in zView); after
  the fix the accessory entries of an application's menu carry a user
  address of a page published read-only to every process, the probe reads
  them, zView survives F10 / Esc / Esc / F10 / Esc under memprot on and
  strict, and TeraDesk/QED now SHOW the accessory titles (HEAD drew the
  entries empty).

CHAIN (verified)
  symbols (llvm-nm, HEAD release kernel and ZVIEW.NAP 9c6497ad):
    ffff000000193af0 size 0x130 = tos_api::aes::menu::ACCS (rustc put the
      `copies` field first: +0x00 = slot 0's title copy, +0x20 = slot 1's)
    ZVIEW.NAP: strstr at file VA 0x4999c (text+0x489a4 = strstr+8, text at
      file VA 0x1000), menu_exec_cmd at 0x1dc24 (lr text+0x1cd64 = 0x1dd64)
  WinDom menu_exec_cmd (sdk/windom/windom-1.21.3/src/menu_execcmd.c): for
    every key not handled elsewhere, starting with titre = entre = 3 (the
    Desk title/box), strstr(ObjcString(menu, entre), cmd) for each entry --
    i.e. it reads the accessory entries' ob_spec strings at EL0.
  EmuTOS (pinned tree): mn_register stores the caller's pointer,
    D.g_acctitle[openda] = pstr "save pointer, like Atari TOS"
    (aes/gemmnlib.c:806); menu_fixup links it into the installed tree,
    tree[ob].ob_spec = (LONG)D.g_acctitle[st++] (:118), called from mn_bar's
    show path (:714) and mn_register (:808). The string is ordinary memory
    the application reads freely.
  NewTOS HEAD: menu_register copies the title into the kernel static ACCS
    (A97: the accessory's own VA is not readable outside its trap), and
    menu_fixup wrote the copy's KERNEL high-half address into every tree --
    including an application's (tos-api/src/aes/menu.rs, HEAD :1368
    t.set_raw_spec(ob, title_copy_addr(st))). EL0 read -> permission fault.
    Side effect seen in this run: the AES itself drew those entries EMPTY in
    every application menu (the owner-aware reader cannot resolve a kernel
    VA in the app's mapping) -- docs/api/aes/accessories.md §9.4 had recorded
    that as "not drawn, never a fault"; the fault is the application's read.

CHANGE (method/acctitle-change.diff)
  tos-api/src/aes/menu.rs
    - title copies moved out of Accs into TITLES: #[repr(C, align(4096))]
      TitlePage, one page, nothing else in it (const-asserted size 4096)
    - titles_user_va(): publishes the page read-only to every process at
      VA = PA on first use (usermem::expose, ProtMode::Pr, ADR-023 -- the
      PPARENT stand-in pattern), cached in TITLES_USER_VA; host: identity
    - title_spec(t, idx): menu_fixup links the kernel address into a
      kernel-built tree (the kernel desktop's bar, read by kernel code only)
      and the published user address into an application's tree (the
      per-reader choice Getmpb and wind_get(WF_SCREEN) make); 0 if the
      publication fails
    - copy_title returns () (the caller never used the address), reinit
      clears TITLES
    - new host test acc_title_tests (1 test)
  docs/api/aes/accessories.md §9.3 (a) (what the copy must not change: who
    can read it), §9.4 (the "not done" bullet closed, its "never a fault"
    claim corrected); docs/api/aes/menu.md note 6 (NewTOS binding).
