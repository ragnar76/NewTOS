DESK10 -- the desktop reaches the system only through traps (G6 of
docs/analysis/desk-aes-gaps-2026-09-14.md).

  kernel/src/desk/ called the GEMDOS leaf functions in tos_api::bdos::fs as plain Rust
  functions with a hand-built TrapArgs, and read the drive bitmap straight out of
  tos_api::bios::drive::drvbits(). Mechanically that is a normal function call that
  happens to carry trap-shaped arguments -- the desktop ran PAST the ABI every
  application uses, so a defect in the dispatcher stayed invisible from the desktop
  (memory `desktop-bypasses-app-abi-path`).

  New: kernel/src/desk/dosbind.rs, the GEMDOS/BIOS counterpart of the aesbind block in
  desk/mod.rs. `svc #1` for GEMDOS and `svc #13` for the BIOS, function id in x8,
  arguments in x0..x7 in TOS order (docs/ARCHITECTURE.md, "Native AArch64 callers").
  One binding per call, named as EmuTOS names them in include/gemdos.h (dos_open,
  dos_read, dos_sfirst, ...); the BIOS call is `drvmap` (EmuTOS `Drvmap`, lowercased per
  CLAUDE.md "Naming Conventions"). The desktop calls no XBIOS function, so there is no
  `svc #14` binding.

THE TWO QUESTIONS THE TICKET ASKED TO SETTLE FIRST -- BOTH ANSWERED, NOTHING HAD TO MOVE

  (a) THE DTA. Fsetdta/Fsfirst/Fsnext keep the current DTA in the RUNNING PROCESS'S
      basepage (p_xdta, EmuTOS bdos/fsmain.c:396-405). During desk::run,
      tos_api::bdos::process::current() is NULL -- the desktop runs in the kernel boot
      context (the same fact desk/mod.rs already documents for appl_init: "the desktop's
      kernel-boot context (null basepage)"). tos-api/src/bdos/fs/find.rs:52-105 routes
      exactly that caller to its KERNEL_DTA cell:

        pub(crate) fn cur_dta() -> u64 {
            let bp = crate::bdos::process::current();
            if bp.is_null() { return KERNEL_DTA.load(Ordering::Relaxed); }
            ...

      The DIRECT call entered find::fsetdta at the identical point, so the trap uses the
      SAME cell and therefore the SAME 44-byte buffer on the desktop's own stack. No
      change, no buffer moved, no path special-cased. (Had the desktop had a basepage,
      set_cur_dta would have truncated the kernel VA to 32 bits -- find.rs:97-105 says so
      in as many words. It does not, so it does not.)

  (b) POINTER ARGUMENTS. A trap from EL0 carries a user VA; the desktop carries a kernel
      high-half VA. The GEMDOS file surface reads its pointers RAW and translates
      nothing: tos-api/src/bdos/fs/mod.rs:23-33 (`cstr`: `let p = ptr as *const u8`),
      bdos/fs/file.rs:297,373 (`ubuf as *const u8`). A83's usermem::resolve_kva is reached
      ONLY from tos-api/src/aes/window.rs:393,474-486 (the window-title reader),
      aes/object.rs:480 and xbios/screen.rs:175-185 -- none of them on this path
      (`/usr/bin/grep -rn resolve_kva tos-api/src kernel/src`, 8 hits, all listed). A
      kernel VA arrives and is dereferenced unchanged.

  Two further properties were checked because the trap path is not only "the same
  function with more steps":
    * IRQs. An exception masks PSTATE.DAIF, so the GEMDOS work now runs with interrupts
      masked. The EMMC driver POLLS -- kernel/src/drivers/bcm2711/emmc.rs:210
      (`wr(IRPT_EN, 0); // poll, don't signal`) -- and every EL0 application already does
      its file I/O this way. No deadlock, no new exposure.
    * The exception stack. An EL1 exception with SPSel=0 runs the handler on SP_EL1, the
      16 KiB emergency stack (link-rpi4.ld:100-102). Only ONE GEMDOS frame is on it at a
      time; the desktop's own recursion (dir_op) stays on the 64 KiB kernel stack. Same
      depth an EL0 app already produces.

ONE NAMED DEVIATION, NOT INTRODUCED HERE AND NOT REMOVED HERE
  EmuTOS's desktop does not read the drive bitmap with BIOS Drvmap at all: it uses
  dos_sdrv(dos_gdrv()) -- Dsetdrv(Dgetdrv()), whose return value IS the bitmap
  (deskapp.c:714). NewTOS reads Drvmap (BIOS 0x0A), which returns the same bitmap from
  the same table (tos-api/src/bios/mod.rs:223-224 -> bios/drive.rs:145). This ticket's
  contract was "behaviour must not change", so the call was rewired onto the trap without
  changing WHICH call it is. Aligning it with deskapp.c:714 is a separate one-line change
  and needs its own ticket.
