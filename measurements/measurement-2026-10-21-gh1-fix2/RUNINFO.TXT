RESULT IN ONE LINE: cause established (the press that cancels a drop-down was not the Control Manager's under the screen lock);
EmuTOS-faithful fix in window::intercept/hctl_window; QED hang gone, GH1 stays fixed, every other shot identical to HEAD.

CAUSE (evidence: checks/diag0-fx2-excerpt.txt = instrumented GH1 tree BEFORE this fix, scenario qedd)
  1 Pointer to "Datei" -> mchange gives the mouse to ctl_pd; the drop-down is tracked (gl_ctmown up).
  2 The press at (300,300) arrives inside the track: "bchange new=1 ... ctmown=true app=false" -- the owner stays ctl_pd
    (EmuTOS aes/geminput.c:334-335, gl_ctmown raised by mn_do aes/gemmnlib.c:277). The track ends on that press: "track -> None button=1".
  3 Our inline Control Manager released the screen at once (ctl_finish(false)) and window::intercept/hctl_window left the press alone,
    because it is in the top window's work area (Gadget::None "belongs to the application"). w_setactive -> set_mown(QED) is refused,
    the button is down ("set_mown 0 button=1").
  4 QED (lock free) takes BEG_UPDATE/END_UPDATE, re-arms evnt_multi and gets the held press from abutton's ownership-blind level test
    ("evnt_multi fired=0x2 pass=0 arm_own=false arm_mb=1"), then wind_update(BEG_MCTRL) with the button down: fm_own's set_mown refuses
    again -> QED holds lock + ml_ocnt=1 while ctl_pd owns the mouse.
  5 The release goes to ctl_pd ("bchange new=0 ... app=false"); w_setactive, the only thing that could hand the mouse back, is gated by
    ctl_may_run() = false because QED holds the lock (GH1 F1, contract point 4). No key/button/rectangle ever reaches QED: the hang
    (Tester: UPDATE_LOCK=1 UPDATE_OWNER=QED MCTRL_CNT=1). HEAD survived only because its w_setactive ran on every pass regardless.
  EmuTOS: after mn_do returns on the cancelling press, ctlmgr's loop (aes/gemctrl.c:439-484) ends its BEG_UPDATE/END_UPDATE, w_setactive
  cannot move the mouse (button down), its next ev_multi(MU_BUTTON, 0x0001ff01) fires at once on the held button (rlr == gl_mowner,
  aes/gemevlib.c:185-198), it takes the screen again, wm_find > 0 -> hctl_window (aes/gemctrl.c:468-470); on the top window's work area
  there is no control point, message stays 0 and ct_msgup(0, ...) waits "while (button & 0x0001) dsptch();" INSIDE the lock
  (aes/gemctrl.c:81-102,182,314). QED's BEG_UPDATE/BEG_MCTRL therefore waits for the release, and fm_own's ct_chgown(rlr) -> set_mown
  (aes/gemfmlib.c:93, aes/geminput.c:220-235) then gives QED the mouse.
  The F1 gate itself (ctl_may_run) is faithful; the missing piece was that hold. Reverting F2 does not help (Tester), as expected.

FIX (uncommitted, working tree)
  tos-api/src/aes/window.rs: hctl_window() -> bool; its Gadget::None arm, when the mouse is not the application's (input::own_mouse()
  false = ctl_pd owns it), consumes the press (ev_consume = ctlmgr's ev_rets, aes/gemevlib.c:268) and returns true; intercept() then
  enters ct_msgup's wait (input::ct_msgup_hold) and keeps the lock as CTL_PD (ctl_finish(true)) while the button is still down;
  input::ct_msgup_busy -> ctl_release hands it to the next waiter on the release (existing GH1 F1 path). A work-area press the
  application owns is unchanged (ctlmgr never sees it in EmuTOS).
  Specs: docs/api/aes/window-graphics.md wind_update (107) contract point 3 + NewTOS mapping; docs/api/aes/menu.md mn_do point 5.
  Host test: tos-api/tests/aes_gh1_update_mutex.rs case 9, two new tests:
    the_press_that_cancels_a_dropdown_holds_the_screen_until_released, beg_mctrl_after_the_cancelling_press_waits_for_the_release.
  checks/diag-fx2-excerpt.txt (same instrumentation, WITH the fix): "track -> None button=1", "intercept held=true", QED's BEG_UPDATE
  finds lock=1 owner=CTL_PD (-2) and parks, release -> "ctl_release owner=-2 wait_len=1" -> QED gets the lock, own=true, key 'x'
  arrives (fired=0x1).
