S2ALL / TSRPAR UNDER PROTECTION -- NOT FIXED BY THE LOADER ORDER
  The loader now allocates the environment first (EmuTOS order). The TSRPAR
  check "TPA beyond blkln back in the pool (< 64 KiB kept)" still fails with
  protection on: TT largest block 0x39f78000 -> 0x39b76000, as in 3b.
  Diagnosis (tsrpar-diag.patch, serial/diag-on-rpi4-tsrlayout-serial.log):
    ON   TSRRES env 0x01e88000, PD/TPA 0x01e89000 (4 MiB), its Mxalloc(64)
         block 0x02289000 = directly behind the TPA -> the Ptermres tail
         0x01e8b000..0x02289000 is a free block of its own.
    OFF  env 0x01497010 and the small block 0x01497020 in a hole below
         (16-byte grain), the tail joins the large free block -> PASS.
  Cause: E9 (fixed 4 MiB TPA, not EmuTOS's largest block) + E16 (page grain)
  + first fit: what a program allocates after its start lies behind its TPA.
  The order was never the cause (3b's guess). Decision for the lead.
  STRICT additionally (serial/c1-strict-rpi4-s2all-crashkernel-serial.log,
  crash kernel answers the prompts): P567 case 6 runs code from the parent's
  PROT_P text in a Pexec-6 child, TSRRES writes the parent's PROT_P mailbox
  -- both are Pexec-0/6 children touching parent-private memory, exactly what
  memprot=strict forbids (FreeMiNT MPF_STRICT, k_exec.c mode 6 = no
  FORK_SHAREVM). With the product kernel the first crash prompt waits for a
  key, so the product strict S2ALL run ends at the prompt (timeout).
