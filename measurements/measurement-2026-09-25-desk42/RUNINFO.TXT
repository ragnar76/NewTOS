0. WHAT THE TICKET ASKED, AND WHAT IS HERE
---------------------------------------------------------------------------
DESK38 built *Show info* functionally; the boxes were hand-laid G_STRING lines
and had, in the user's words, nothing in common with EmuTOS's.  DESK42 rebuilds
the two resource trees object for object -- same order, same object numbers,
same labels, same measurements resolved the way `rsrc_obfix` resolves them.

  ADDISKIN  desk_rsc.c:709-768, desk_rsc.h:75-84  -- 10 objects, 38 x 12+8
            character cells = 304 x 200 px
  ADFFINFO  desk_rsc.c:622-703, desk_rsc.h:61-72  -- 14 objects, 40 x 16
            character cells = 320 x 256 px

Both dumped object by object at run time (serial/dlg-dumps.txt) so the tree can
be diffed against the resource without reading our source.

5. d42d -- the STRENAME retry loop
---------------------------------------------------------------------------
serial/d42d-serial.log, screendumps/d42d-*.png.  `while(1)`
(deskinf.c:551-635) is the part of `inf_file_folder` NewTOS did not have; the
rename lived in the caller and a failure ended it.

One dialog pass ticks Read-Only *and* shortens the name (one Backspace,
"README  TXT" -> "README  TX").  EmuTOS's order then produces the failure by
itself: the attribute is written first (`:591-605`) and the rename attempted
afterwards (`:616-626`), and a Read-Only file cannot be renamed
(`xrename`: `if (fcb->f_attrib & FA_RO) return EACCDN`, bdos/fsdir.c:943-944).

  d42d-e-short.png     the field reads "Name: README  .TX_"
  d42d-f-strename.png  STRENAME: "Rename error!" with [Retry] [Cancel]
                       -- desk_rsc.c:2557, verbatim
  d42d-g-retry.png     Retry re-shows the SAME box with the attempted name
                       still in it and Read-Only now selected (the attribute
                       was written on the first pass) -- the `:632-633` comment
  d42d-h-end.png       Cancel leaves it; C:\README.TXT is still there with
                       attr=0x21 (serial/lsimg.txt)

6. SIDE FINDING, NOT A DESK42 BEHAVIOUR: GEMDOS `Frename` takes an empty name
---------------------------------------------------------------------------
serial/d42e-serial.log, screendumps/d42e-*.png, serial/lsimg.txt.

Empty the name field (11 x Backspace) and press OK.  EmuTOS has no empty-name
special case either: it unformats the field into `dstpth+nmidx` and calls
`dos_rename(srcpth, dstpth)`, so the destination is the bare directory `C:\`
(deskinf.c:600-626).  EmuTOS's GEMDOS refuses that -- `xrename` opens with
`if (!ixsfirst(p2,FA_SUBDIR,0)) return EACCDN` (bdos/fsdir.c:912-913).

Ours does not.  `Frename("C:\\README.TXT","C:\\")` returns E_OK and the
directory entry is rewritten with an ALL-BLANK 8.3 name:

  d42e.img root, entry 2:   (no name)   64  attr=0x20
  the window shows an unlabelled file icon (d42e-e-afterok.png)

The cause is generic, not rename-specific: `tos-api/src/bdos/fs/dir.rs:148`
`fcb_name("")` returns `Some([b' '; 11])`, an all-blank FCB name, and every
GEMDOS entry point that takes a final path component goes through it.

This is a GEMDOS defect, not a desktop one, and it is NOT fixed here (DESK42's
scope is the two trees).  DESK42 does make it *reachable*: the box NewTOS had
before rejected an empty name in the desktop, which EmuTOS does not do, so the
call was never issued.  It needs its own ticket.

`fsck_msdos -n` does not flag the blank entry -- an all-blank name is
structurally valid FAT, merely an illegal 8.3 name.

8. WHAT ONLY THE REAL PI CAN CONFIRM
---------------------------------------------------------------------------
Every gesture here is driven by the scratch-copy IKBD injector, and every
keystroke is a raw IKBD byte fed into `crate::ikbd::feed` -- which is where the
IKBD driver itself delivers, so the code path is the same.  A real mouse click
on a radio button, a real Backspace in the edit field, and `count_ffs` over the
four real partitions (Pi checklist item 69) are real-Pi4 only.
