HOW ZVIEW IS STARTED WITH A FILE
  #Z cannot pass arguments, so C:\ZVLAUNCH.NAP (method/zvlaunch.c, test
  helper) reads C:\ZVARG.TXT and calls shel_write(SHW_EXEC, 1, 0,
  "C:\ZVIEW\ZVIEW.NAP", tail) after Dsetpath(C:\ZVIEW). The Dsetpath is
  needed: EmuTOS' sh_write saves the CALLER's directory as the new
  program's start directory (aes/gemshlib.c:173-175, sh_curdrvdir(sh_apdir)),
  NewTOS does the same. The first launcher version omitted it: zView started
  in C:\, zview_path "C:", no C:\codecs -> its own "can't load the plugins"
  alert (method/plprobe.c, first run: "zview_path=[C:]", "chdir([C:\codecs])
  = -1"); faithful behaviour, launcher fixed. Second plprobe run
  (serial/plprobe-serial.log): zview_path C:\ZVIEW, chdir ok, opendir/readdir
  list the ten *.nld, ldg_open(BMP.NLD) ok, plugin_init found, infos "BMP".

FINDING K1 (kernel AES/VDI, blocks the acceptance; checks/k1-evidence.txt)
  graf_handle returns 1 (tos-api/src/aes/graf.rs:590, EmuTOS gl_handle);
  NewTOS never opens VDI handle 1 (kernel/src/desk/vdibind.rs:16-26), so
  vwk::resolve(1) fails and the VDI treats every call on it as a no-op
  (tos-api/src/vdi/mod.rs:416-422). EmuTOS opens it at AES start
  (aes/gemgsxif.c:169-185 gsx_wsopen -> v_opnwk(…, &gl_handle, …)).
  VQPROBE.NAP (method/vqprobe.c): vq_extnd(1, 0|1) leaves work_out
  untouched; on a v_opnvwk handle it answers planes 16.
  WinDom ApplInit (appl_init.c:42-46) therefore sets app.color = 0,
  app.nplanes = 0 in every WinDom program; zView builds its picture MFDBs
  with app.nplanes planes (pic_load.c:34): fd_nplanes 0 (ZVIEW-DBG.NAP,
  serial/alt-dbg1-serial.log "np=0"), 256-byte buffer (mfdb.c:35), LnSize 0
  (pic_load.c:109). Effects measured:
    probe-t24-bmp  (product, 64x48 BMP): window with the right info line
                   "64x48x24", content grey (LWHITE), toolbar empty
    probe-t-pi1    (product, 320x200 DEGAS): Bus Error at text+0x17b60 =
                   WinDom DataSearch+8, FAR 0xf800f800f800f800 = four red
                   RGB565 pixels -- the 640-byte rows overrun the 256-byte
                   block into WinDom's window data list
  Fix belongs in the kernel (open a physical workstation for gl_handle as
  EmuTOS does, or resolve handle 1 to the screen device). NOT done (task
  rule: no kernel changes; STOP and report). Toolchain workaround in WinDom
  rejected: it would hide a kernel/EmuTOS divergence every WinDom program
  hits.

FINDING U1 (upstream zView TGA codec, not changed)
  tgaldg.c fill_img_buf (:304-327): img_buf holds 2*line_size bytes and is
  refilled only when img_buf_offset >= half of it; nothing checks that the
  next line's packets are all in the buffer. After a line just under half
  (no refill), a following line longer than the bytes left reads stale
  buffer bytes. A model of exactly that logic over P.TGA's packet sizes
  predicts underruns at rows 84, 93, 114, 134, 158, ... = the first faulty
  rows on the screen. Synthetic reproduction (in the repo):
  method/gen-tga-refill.py -> bin/TREFILL.TGA (270x48, lines of 806 and
  820 bytes alternating; Pillow decodes it to checks/TREFILL.TGA.rgb), model:
  underrun from row 2; run file-on-trefill-tga: zView ends with libshare's
  "malloc.c:256: free: Assertion `s == r' failed" (heap corrupted by the
  stale-data decode), desktop returns (screendumps/file-on-trefill-tga-t30.png).
  Pure C, endian-neutral -- the same on the 68k. Atari source unmodified.
