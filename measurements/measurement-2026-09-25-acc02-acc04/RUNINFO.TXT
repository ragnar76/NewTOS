0. Scaffolding, and why (scratch copies only, never the shared tree)
-------------------------------------------------------------------
method/make_scratch.sh rsyncs the crates into the job scratch and applies, in
order:

  a79_patch_desk10.py   H02 serial AES trace + the "[desk] desktop up" flag
  apply_injector.py     the scripted IKBD injector + the run's SCRIPT
  a78_patch2.py         dual arming / script selection
  key_step_patch.py     Step::Key
  acc_inject_patch.py   NEW, this batch: arm the injector on the DESKTOP ONLY

The last one exists because of this batch's own subject matter. a78_patch2.py
picks the script from whichever context armed the injector first — an EL0
program or the desktop. A desk accessory IS an EL0 process and it runs BEFORE
the desktop (EmuTOS `geminit.c:736-737`), so it armed the injector and every
later step was taken from the empty SCRIPT_TERA. The gate is now simply "the
desktop is up".

Two further scratch-only patches were used for the diagnosis in section 5 and
are NOT part of any run below (they are in method/ for reproducibility):
ident_trace_patch.py (AES identity + raw control words in the trace) and
elr_probe_patch.py (the EL0 return address of every GEM trap).

5. The two defects this batch found in itself, and how
------------------------------------------------------
Both were found by running, not by reading, and both are fixed in the diff.

(a) THE ACCESSORY'S MENU TITLE IS AN EL0 POINTER.
    `menu_register` stores the caller's string pointer, as EmuTOS does
    (`gemmnlib.c:806`, "save pointer, like Atari TOS"). Writing that pointer
    into the DESKTOP's menu tree and letting the drop-down renderer
    dereference it at EL1 is a data abort — measured, ESR=0x96000004,
    FAR=0x1610, on the first hover over *Desk*. This is the A97 class of
    defect: one address space in EmuTOS, several here. Fixed by copying the
    title into a kernel-side table at registration (where the accessory IS the
    current process and the read is safe) and splicing the COPY's address into
    the tree. Named deviation, documented at `Accs::copies`.

(b) THE SCHEDULER SWITCH DID NOT PRESERVE THE FP/SIMD REGISTERS.
    After the GEM program in step 2 had run, the resumed accessory trapped
    into the AES with the WRONG OPCODE on every pass, forever — 110 484 calls
    to `appl_exit` from a program whose source never calls it. Diagnosed with
    ident_trace_patch.py (it is identity 0, an accessory) and
    elr_probe_patch.py (the same `svc` site, sysacc's `aes_call` loop), then
    settled by disassembling the accessory: clang keeps the AES control block
    `{23, 0, 1, 1}` in **d1** as a loop-invariant constant and stores it with
    `str d1, [x9]` before each trap. `ExceptionFrame` carries only the GPRs,
    so the hard-float GEM program's leftover `d1` became the accessory's
    opcode. Fixed by saving/restoring `v0..v31` + FPCR + FPSR across a
    scheduler switch (`FpContext`, `save_fp_context`/`restore_fp_context`).
    Only a second EL0 context can trigger it, which is why it had never
    appeared before accessories existed.
