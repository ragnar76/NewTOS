RESULT IN ONE LINE
  Not a kernel deviation: zView's own text renderer draw_text()
  (zview/custom_font.c:159-205) builds each glyph's 1-plane MFDB with a
  byte walk that is only right on a big-endian machine; on little-endian
  AArch64 every glyph row lands in bits 7..0 of its WORD, outside the 2..8
  columns vrt_cpyfm copies, so nothing is drawn. Fixed by a toolchain
  overlay (sdk/zview/overlay/zview/custom_font.c); names now drawn in black
  (tiles, tree), white on the selection, sizes in LBLACK.

CAUSE CHAIN (with evidence)
  1. Every name in the browser goes through draw_text():
       catalog/catalog.c:857,889,920,993,1020 (tiles, size line, edit,
       selected) and catalog/catalog_mini_entry.c:192,195 (tree)
     (/usr/bin/grep over the pristine tree sdk/zview/z-tools-04805b7/zview).
  2. draw_text() (custom_font.c:181-201): per character a 16x8 1-plane MFDB
     fx_mem[16]; the glyph's 8 row bytes are copied from the WORD table
     my_font_8[] with char pointers, "*dest = *model++; dest += 2"
     (:182-183, :188-195), then vrt_cpyfm(handle, MD_TRANS, ...) with
     source columns 0..ofwf[c]-1 (2..8 pixels wide, :197-201).
     On the 68k the byte at an even address is the WORD's high byte =
     pixels 0..7, and the table bytes come out in row order.
  3. NewTOS reads an MFDB form as host-order 16-bit WORDs, bit 15 leftmost
     (tos-api/src/vdi/backend.rs MonoBits::word / MonoSrc, raster.rs
     vrt_cpyfm) -- the same contract as EmuTOS, which reads the form as
     native UWORDs with mask 0x8000 >> x (references/emutos/vdi/
     vdi_raster.c:1241-1243 vrt_cpyfm16; :1257-1260). The SDK's other
     forms (icons, RSC images) are native WORDs (ADR on the native RSC,
     docs/MEMORY.md:383-400), and zView's icons draw correctly.
  4. On little-endian the byte walk writes the LOW byte of each WORD
     (pixels 8..15) and swaps every row pair. Host proof with the UNCHANGED
     draw_text() (method/fontprobe: a stand-in general.h whose vrt_cpyfm
     records the form as the NewTOS VDI reads it):
       glyph cols 0..5 words: 0004 007c 0010 0008 0040 0020 0000 007c  -> NO PIXELS
     for "ZVIEW": every glyph "NO PIXELS"; with the overlay:
       glyph cols 0..5 words: 7c00 0400 0800 1000 2000 4000 7c00 0000  -> pixels
     and the word renders as readable ASCII art.
     Host test sdk/zview/tests/custom-font-host.c over all 255 characters:
       pristine (checks/red-custom-font-host-pristine.txt):
         1816 mismatches, 0 glyph rows with pixels in the copied columns, rc=1
       overlay  (checks/green-custom-font-host-overlay.txt):
         0 mismatches, 1545 glyph rows with pixels, rc=0
  5. QEMU repro (screendumps/before-Z05_TREE.png, before-Z03_LATER.png,
     product ZVIEW.NAP 9c6497ad...): browser on C:\, tree expanded, tiles
     with folder/file icons, no text anywhere -- the user's photo.
     The selected tile shows only the grey selection bar (white text on it
     is empty as well).
