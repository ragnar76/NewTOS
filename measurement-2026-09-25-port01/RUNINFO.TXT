1. INJECTOR (method/port01_patch.py)
---------------------------------------------------------------------------
a78_patch2.py's dual arming picks the empty SCRIPT_TERA whenever an EL0
process is the running one at the first injector tick. Since commit 03394c2
the boot starts two desk accessories, which are EL0 processes scheduled before
the desktop appears, so the first tick always sees one and NO action fired
(first probe run: `[h02] injector armed` during `[sched] switch -> slot 0`,
then nothing for 200 s). port01_patch.py replaces the dual arming with the one
case this ticket needs: step only once "[desk] desktop up" has set DESK_UP,
and always run SCRIPT_DESK. The clock then starts at the desktop, which is
what the action lists' timings assume.

4. RESULT: the argument reaches the application (the ticket's defect)
---------------------------------------------------------------------------
before (serial/port01-before-serial.log:616-619):
    ARGVTEST: cmdlin len 13 raw "C:\README.TXT"
    ARGVTEST: argc 1
    ARGVTEST: argv[0] ""
    ARGVTEST: argv terminated

after (serial/port01-after-serial.log:515-519):
    ARGVTEST: cmdlin len 13 raw "C:\README.TXT"
    ARGVTEST: argc 2
    ARGVTEST: argv[0] ""
    ARGVTEST: argv[1] "C:\README.TXT"
    ARGVTEST: argv terminated

Both lines come from ONE program in ONE run: the first is read out of the
BasePage through mintlib's BASEPAGE struct, the second is what the startup
built. Before, the kernel's tail arrives and the startup drops it; after, it
survives. That is the whole defect.

Candidate 2 of the ticket (the LP64 basepage) is ruled out by the same pair of
lines: the `cmdlin len 13 raw "C:\README.TXT"` line is read through
`_base->p_cmdlin`, i.e. through the mintlib BASEPAGE struct, and it is right
in BOTH runs.

6. SECOND, INDEPENDENT DEFECT (not fixed here -- for a new ticket)
---------------------------------------------------------------------------
Measured, not inferred (serial/trace-serial.log:1033):
    [port01] Fopen len 12 path "C:\\README.TX"      (Rust {:?}, so \\ = one \)
QED asks the file system for a name one character short. Read at the source:

  * cflib `make_normalpath` (sdk/cflib/cflib-21/fsnorm.c:85-95) appends a
    trailing `\` and then REMOVES it again unless `path_exists()` says the
    result is an existing DIRECTORY;
  * `path_exists` (fsexists.c:35-45) is `Fattrib(p,0,0) >= 0 && (attr&FA_DIR)`,
    so for a file path it is false on TOS 1-3, on TOS 4 and on EmuTOS alike
    (EmuTOS `xchmod` -> `findit` on "C:\README.TXT\" -> EPTHNF,
    references/emutos/bdos/fsdir.c:402-411);
  * QED removes the separator UNCONDITIONALLY -- src/poslist.c:53-54
    (`make_normalpath(...); filename[strlen(filename)-1] = '\0';`) and the
    same pattern in src/dd.c:99-101 -- i.e. it is written against a
    make_normalpath that ALWAYS leaves the separator.

Our fsnorm.c is byte-identical to the pristine cflib-21 tarball (verified),
so this is not a porting error we introduced; QED and cflib-21 are a
mismatched pair.

CONFIRMED end to end, scratch only: with `make_normalpath` keeping the
separator it appended (method/cflib_normalpath_experiment.py, one line, via
the watched sdk/cflib/overlay/ channel), QED asks for the right name and opens
the file -- serial/exp2-serial.log:1033 `Fopen len 13 path "C:\\README.TXT"`,
screendumps/exp2-qed.png (window titled C:\README.TXT with the file's two
lines in it).

NOT landed: the change alters a vendored upstream library's behaviour for
every cflib caller (filesel.c:205,227,265 inside cflib; clipbrd.c:281,
dd.c:99, global.c:433, poslist.c:53, projekt.c:938 in QED) and hence every
ported cflib application. Which side is to be corrected -- cflib via
sdk/cflib/overlay/, or a different cflib version -- is a decision for the
lead, not for this ticket.
