# LIBC-TTY: mintlib isatty / read on the NewTOS console (2026-10-13)

Scope: TASK/LIBC-TTY.md, researcher step. Docs/analysis only. Basis: main at
8264026c. Paths below are repo-relative; `mintlib/` = `sdk/libc/mintlib/`
(extracted from `sdk/libc/mintlib-0.60.1.tar.xz`, gitignored).
Label: **[R]** = read in code this session, **[I]** = inference.

## 0. Zusammenfassung

1. Upstream `__isatty` (`mintlib/mintlib/isatty.c:16-66`) braucht auf TOS nur
   zwei GEMDOS-Aufrufe: `Fcntl(fd,&dummy,TIOCGPGRP)` (muss `-ENOSYS` = `-32` =
   EINVFN liefern) und die `Fseek`-Probe (`Fseek(1,fd,SEEK_CUR)==0` heisst tty).
   Es setzt dabei `status` und `flags = CRMOD|ECHO` (`:54-62`). Es zieht
   *kein* `ioctl()`: es ruft das `Fcntl`-Makro direkt. [R]
2. Der Shim `newtos-arch/isatty.c` entstand im Erstport (Commit bbf45898,
   einziger Commit der Datei). Seine Begruendung ("pulling the ioctl/tty
   machinery") trifft fuer `isatty.c` selbst nicht zu (kein ioctl-Aufruf); der
   reale Grund war vermutlich, dass `Fseek` auf Geraeten damals nicht 0
   lieferte (bis FS10 `EBADF`, `docs/sdk/07-mintlib-limits.md:186`). [R fuer den
   Commit und die Kommentare, I fuer das "vermutlich"]
3. **Upstream `isatty` funktioniert nach FS10 auf NewTOS unveraendert.** Jeder
   GEMDOS-Aufruf ist unten gegen den Kernel nachverfolgt; kein Unterschied zu
   EmuTOS gefunden. Der Shim kann entfallen.
4. Die "zwei Tasten pro Byte"-Eigenschaft ist **Upstream-Verhalten von mintlib
   0.60.1** (`unix/read.c` ist byte-identisch zum Tarball), keine NewTOS-
   Divergenz. `Crawcin` liefert auf NewTOS wie auf EmuTOS das gepackte LONG.
   Auf echtem TOS wird der RAW-Weg nur erreicht, wenn ein Programm RAW/CBREAK
   setzt oder ECHO loescht; mit dem Shim wird er faelschlich *immer* genommen.
5. Zusaetzlicher Befund: der ioctl-Shim kennt `TIOCGETP/TIOCSETP` nicht
   (siehe 4.4); der Teil des RAW-Wegs, den Programme bewusst anschalten, bleibt
   also auch nach dem Fix nicht erreichbar.

## 1. Was upstream `__isatty` auf TOS (`__mint == 0`) tut

Quelle: `mintlib/mintlib/isatty.c` (byte-identisch zum Tarball [R]).

| Zeile | Schritt |
|---|---|
| `:19,23-24` | `handle = fd+3` (`__OPEN_INDEX`, `mintlib/lib.h:114`); ist `status != FH_UNKNOWN`, Cache-Treffer (`FH_UNKNOWN=0, FH_ISATTY=1, FH_ISAFILE=2`, `lib.h:116-118`) |
| `:28` | `Fcntl(fd, &dummy, TIOCGPGRP)` = Trap `0x104` (`mint/mintbind.h:80`) |
| `:29` | nur bei Ergebnis `== -ENOSYS` (Userland `ENOSYS`=32, `mint/errno.h:20,258`, also `-32` = EINVFN) weiter zum Seek-Trick; sonst `rc = (retval == 0)` (`:50-52`) |
| `:33` | `oldloc = Fseek(0, fd, SEEK_CUR)` |
| `:36` | `Fseek(1, fd, SEEK_CUR) != 0` -> **Datei** (`rc=0`), Position zurueck mit `Fseek(oldloc, fd, SEEK_SET)` (`:44`) |
| `:46-48` | Ergebnis `0` -> **tty** (`rc=1`) |
| `:54-61` | Cache: tty -> `status=FH_ISATTY, flags=CRMOD|ECHO`; sonst `FH_ISAFILE` |

Was das System liefern muss:

* Trap `0x104` muss `-32` liefern (nicht implementiert). EmuTOS:
  `bdos/bdosmain.c:442-445` (`fn > MAX_FNCALL -> EINVFN`), also dasselbe. [R]
* `Fseek` auf ein Zeichengeraet (-1/-2/-3, Std-Handles 0-2 mit Standardmapping)
  muss `0` liefern, egal welcher Offset/Modus. EmuTOS: Geraeteblock in `osif`,
  endet mit `return 0` (`bdos/bdosmain.c:~571-642`, Zeile 640-641). [R]
* `Fseek` auf eine echte Datei liefert `pos+1` bzw. `ERANGE`, nie `0`, weil
  `ixlseek` (`bdos/fsio.c:354-361`) bei `n > o_fileln` oder `n < 0` `ERANGE`
  gibt und ein erfolgreiches `Fseek(1,..,CUR)` die Position `>= 1` liefert. [R]

Erkennung von auf eine Datei umgelenkten Handles: `Fforce(1, fh)` laesst
Handle 1 auf einen SFT-Eintrag zeigen; `Fseek` loest dann auf eine Datei auf
(kein Geraet), die Probe liefert `!= 0`, also `FH_ISAFILE`. Es gibt keinen
Fstat/Finstat/Foutstat-Pfad; `Finstat/Foutstat` benutzt `isatty.c` nicht. [R]
Einschraenkung: der Cache (`status`) wird nur von `open/close/dup/dup2/pipe/
ioctl(TIOCSCTTY..)` zurueckgesetzt (`unix/open.c:343`, `close.c:24-25`,
`dup.c:29`, `dup2.c:32`, `pipe.c:26-28`, `mintlib/main.c:161-162`). Ein
`Fforce()` direkt im Programm nach der ersten `isatty`-Abfrage bleibt
ungesehen (Upstream-Eigenschaft, auch auf TOS). [R]

## 2. Warum der Shim existiert und ob upstream jetzt laeuft

### 2.1 Historie

`git log -- sdk/libc/newtos-arch/isatty.c` = nur `bbf45898` ("port mintlib
libc to NewTOS/aarch64", 2026-07-18). Kommentar im Shim: mintlib probiere
"with Fcntl(TIOCGPGRP) and a seek trick, pulling the ioctl/tty machinery";
"the console is fds 0,1,2 and everything else is a file, so isatty is a fixed
fd-range test" (`newtos-arch/isatty.c:2-6`). Der Shim definiert zusaetzlich
`__open_stat[]` (`:16-21`, `:22`), weil `mintlib/isatty.c` ausgeschlossen ist
(`build-libc.sh:168`, Kompilierung `:258`). Der Commit-Text nennt das Ziel:
"cutting the Unix time/uid/passwd tail ... ioctl" - gemeint ist das
`do_fstat.c`-Ende (dort ruft upstream `ioctl`), nicht `isatty.c` selbst.
Der ioctl-Bezug von `isatty.c` besteht nur im Header `sys/ioctl.h` fuer die
Konstante `TIOCGPGRP`. [R]

Der Shim ist zugleich eine Abhaengigkeit: `do_fstat.c` meldet fds 0-2 immer als
`S_IFCHR` (`newtos-arch/do_fstat.c:76-79`), `stdio_init.c:50-57` fragt dann
`__isatty`.

### 2.2 Spur jedes Aufrufs gegen NewTOS

| Aufruf | NewTOS | Beleg | Ergebnis | EmuTOS gleich? |
|---|---|---|---|---|
| `Fcntl` (0x104) | `id > MAX_FN` (`MAX_FN = 0x57`) -> `EINVFN` (-32) vor jeder Argumentauswertung | `tos-api/src/gemdos/mod.rs:32,151-153` | `retval == -ENOSYS` | ja, `bdosmain.c:442-445` |
| `Fseek` auf Handle 0-2 (Standard) | `resolve()` -> `Target::Device` -> `return 0` | `tos-api/src/bdos/fs/file.rs:231-246,914-922` | tty | ja (FS10, Spec `docs/api/gemdos/file/42-fseek.md` "Character-device and standard handles") |
| `Fseek` auf -1 (isatty(-1)) | `FOfd::Bios(-1)` -> Device -> 0 | `file.rs:237-239` | tty (siehe Risiko 5.3) | ja |
| `Fseek` auf Datei, Pos `p<size` | `ixlseek(base+1)` -> `p+1` | `file.rs:923-934`, `bdos/fs/fsio.rs:324-` | `!= 0` -> Datei, Rueckseek per `SEEK_SET` | ja (`fsio.c:321-361`) |
| `Fseek` auf Datei am EOF / leer | `n > fileln` -> `ERANGE` | `fsio.rs:325-327` | `!= 0` -> Datei | ja (`fsio.c:360-361`) |
| `Fseek` auf geschlossenes Handle | `Target::None` -> `EIHNDL`; Geraet < -3 -> `EIHNDL` | `file.rs:242,921` | `!= 0` -> "Datei" (wie auf TOS) | ja (`bdosmain.c:~600-602`) |

Ergebnis: FS10 (Fseek auf Geraeten = 0) war die fehlende Voraussetzung, FS11
(Fread/Fwrite-Geraetepfad) braucht `isatty` nur fuer die flags-Logik. Es gibt
keinen NewTOS-Unterschied zu EmuTOS in diesen sechs Faellen. [R]
Nicht geprueft: dass die QEMU/Pi-Laufzeit das tatsaechlich so zeigt (kein
Lauf, nur Quellspur). [unverifiziert]

### 2.3 Nebenwirkungen eines Wechsels (jeweils [R] soweit zitiert)

* `isatty(fd)` wird nach jedem `open()` gerufen (`unix/open.c:347`): +3 `Fseek`-
  Traps je `fopen`/`open`, Position wird am Ende wiederhergestellt. Kosten: 3
  Traps, bei `p=0` ohne FAT-Kettenlauf (`ixlseek n==0`). [I zur Groessenordnung]
* `unix/write.c:29-43`: bei tty UND (`RAW` oder `signal(SIGINT)` gesetzt) schreibt
  `write` bytewise ueber `Fwrite`, mit LF->CRLF falls `CRMOD`. Bisher `flags=0`
  -> kein `\r`. Nach dem Fix: Programme mit installiertem SIGINT-Handler bekommen
  `\r\n` fuer jedes `\n` (TOS-typisch; EmuTOS `tabout` uebersetzt nicht, `bdosmain.c:~626-632`).
  Ohne Handler gilt der normale `Fwrite`-Pfad unveraendert.
* `unix/read.c:150-170` (Fread-Pfad, tty): `0x04` am Anfang -> EOF (`t_eofc`
  = Ctrl-D, `read.c:25,152`); Zeile ohne `\r` bekommt `\r` angehaengt, `CRMOD`
  macht daraus `\n` und gibt zusaetzlich `Cconout('\n')` aus (`:166-169`) -
  das ist das von FS11 Probe C gemessene Verhalten.
* `mintlib/main.c:168`: `isatty(2)` bleibt wahr -> `Fforce(2,-1)` wie bisher
  (LIBC-MAIN); wird stderr aber per `Fforce` auf eine Datei gelenkt, entfaellt
  das nun korrekt.
* `main.c:195`: `!isatty(1)` -> `stdout` voll gepuffert, wenn umgelenkt (bisher
  nie; `do_fstat` meldet aber weiter CHR, siehe 4.3).

## 3. mintlib `__read`, RAW-Weg (`unix/read.c:172-218`)

Auswahl: `__mint>0 || flags==-1 || (flags&(RAW|CBREAK|ECHO))==ECHO` -> `Fread`
(`:70-71`); sonst RAW-Weg. `flags` kommt aus `__open_stat[].flags` nur wenn
`isatty(fd)` (`:59-66`), sonst `-1` -> `Fread`. [R]

Mit dem Shim: `isatty(0)=1`, `flags=0` (nie gesetzt) -> `0 & ... != ECHO` ->
RAW-Weg fuer jedes `read(0,..)`.

"Zwei Tasten pro Byte, erste verworfen": `:176` `r = _console_read_byte(fd) &
0xff;` liest eine Taste und ueberschreibt `r` danach (`:184`) ohne sie zu
benutzen; `:183` liest die naechste. Auch der Scancode-Zweig `:177-181` laeuft
erst *nach* dem Verwerfer. `_console_read_byte` (`mintlib/console.c:17-33`)
ruft zuerst `Fgetchar(fd,0)` (Trap 0x107, auf NewTOS wie EmuTOS `-32` ->
Fallback), dann `Crawcin()` fuer fd 0. [R]

**Ist das NewTOS-Divergenz?** Nein.
* `unix/read.c` und `mintlib/console.c` sind byte-identisch zum Tarball [R]
  (`diff`), die doppelte Leseschleife ist Upstream.
* `Crawcin`: EmuTOS `xrawcin` = `getch(HXFORM(run->p_uft[0]))`
  (`bdos/console.c:375-378`), Rueckgabe das volle gepackte LONG
  (Scancode Bits 16-23, ASCII Bits 0-7). NewTOS `crawcin` =
  `chardev::bconin_handle(DEV_CON)` = gepacktes Key-LONG, kein Echo, kein Ctrl-C
  (`tos-api/src/gemdos/console.rs:251-254`). Gleiche Semantik. [R; die
  Verbindung `getch`->`Bconin`-Rueckgabe nicht Zeile fuer Zeile verfolgt,
  `console.c:351-370` nur bis zum Typeahead-Teil gelesen -> kleine Luecke]
* Auf echtem TOS ist der RAW-Weg also ebenfalls doppelt lesend; er faellt dort
  nur selten auf, weil `isatty` ECHO|CRMOD setzt und der Weg nur bei explizitem
  RAW/CBREAK (ueber `ioctl TIOCSETP`, `unix/ioctl.c:176-189`) oder nicht
  gesetztem ECHO erreicht wird. [I] Ob 0.60.1 dort ein Regressions-Bug ist,
  oder `:176` ein Rest eines anderen Konzepts, ist aus dem Quelltext nicht
  entscheidbar (kein Upstream-ChangeLog-Beleg gesucht). **Offen.**

## 4. Vorschlag

### 4.1 Minimaler korrekter Fix (empfohlen)

Den Shim entfernen und mintlibs `mintlib/isatty.c` bauen:

1. `build-libc.sh`: `mintlib/isatty.c` aus `EXCLUDE` (`:168`) nehmen, den Eintrag
   `newtos-arch/isatty.c -> arch__isatty.o` (`:258`) und den Kommentar (`:149`)
   entfernen; `__open_stat[]` kommt dann wieder aus mintlib (`isatty.c:14`).
   `newtos-arch/isatty.c` loeschen. Folgt aus 2.2.
2. `docs/sdk/07-mintlib-limits.md:50` und `:186` ("isatty = fds 0-2") und
   `docs/MEMORY.md:1208`, `docs/sdk/04-porting-anatomy.md:81`,
   `build-libc.sh:149` anpassen.
3. Host-Test `sdk/libc/tests/fstat-host.sh` (baut den Shim, "minus weak_alias",
   Kopf `:5-8`) auf `mintlib/mintlib/isatty.c` umstellen und `Fcntl` im
   `fstat-host-gemdos.h` hinzufuegen (liefert -32).

Alternative (Overlay reparieren, **nicht empfohlen**): Handles 0-2 per
`Fseek`/`Fstat` unterscheiden, `status`+`flags` setzen und `isatty(-1)`
behandeln = Nachbau von 1:1 derselben Logik; schafft eine zweite Pflege-
stelle ohne Gewinn. Ein Teil-Fix (nur `flags=CRMOD|ECHO` im Shim) behebt den
Lesepfad, laesst aber die Umlenkung (`Fforce`) falsch.

### 4.2 Betroffene Programme (nur aus Quelltext-Grep, nicht gelaufen)

* libc-basierte Programme, die `getchar/fgets/scanf/read(0)` benutzen. Der
  Grep ueber `sdk/apps` ergab im C-Code nur Logging/Hilfs-Treffer (highwire,
  qed/test/hilight.c, coremark README); eine Nutzung von `stdin` in QED,
  TeraDesk, Doom, APITEST ist **nicht** belegt (nur FS11-Offen-Liste nennt sie
  als Regressionsstichprobe). `stdio_init`/`main.c` rufen `isatty` aber in
  **jedem** libc-Programm (`main.c:168,195`, `stdio_init.c:56`): alle sind
  betroffen (Pufferung/stderr).
* EmuCON ist laut Grep Kernel-Rust (`kernel/src/shell*.rs`), kein libc-Programm;
  nur indirekt ueber Programme, die er startet. [R fuer Dateien, I fuer
  "nicht betroffen"]

### 4.3 Risiken / Folgearbeit

1. `do_fstat.c` meldet 0-2 weiter als `S_IFCHR` auch bei Umlenkung
   (`newtos-arch/do_fstat.c:76-79`): `fstat(1)` luegt, `stdio_init` waehlt
   korrekt dank `isatty`. Eigenes Ticket sinnvoll.
2. Ein Programm, das `Fforce` direkt nach der ersten `isatty`-Abfrage aufruft,
   sieht den Cache-Stand (Upstream).
3. `isatty(-1)` wird wahr (`Fseek` auf -1 = Geraet). Upstream erwartet das
   (`open.c:347`: `isatty(rv) && !O_NOCTTY && !isatty(-1)` - nur fuer tty-
   Opens relevant). Beim Shim war es 0. [R, Wirkung I]
4. `write.c` LF->CRLF nur bei RAW oder SIGINT-Handler (siehe 2.3).
5. Der Fread-Pfad macht `Cconout('\n')` (read.c:168) - Doppel-Newline-Gefahr
   nur, wenn der NewTOS-`cgets` selbst ein LF ausgibt; FS11 Probe C zeigt es
   nicht (Beleg laut Ticket, Log nicht erneut gelesen). [unverifiziert hier]
6. ioctl-Shim ohne `TIOCGETP/TIOCSETP/TIOCGETD/...` (`newtos-arch/ioctl.c:23-29`
   leitet nur an `Fcntl`): `ioctl(0, TIOCSETP, ...)` und `tcsetattr` liefern
   `-1`/EINVFN statt `__open_stat[].flags` zu setzen (`unix/ioctl.c:176-199`
   macht das upstream). Programme, die RAW/CBREAK ueber ioctl wollen, bleiben
   auf diesem Weg tot - unabhaengig vom isatty-Fix. Ob der upstream-Fallback
   ohne die m68k-`Super()`-Teile (`linea0`, `TIOCGWINSZ`) uebernommen werden
   soll, ist eine **Entscheidung** (siehe 6).
7. Der RAW-Weg selbst (Doppellesen) bleibt ein latenter Upstream-Bug fuer genau
   diese Programme; ein SDK-Overlay-Patch von `unix/read.c:176` waere eine
   bewusste Abweichung von mintlib.
