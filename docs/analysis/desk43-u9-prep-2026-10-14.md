## 0. Ergebnis in zehn Sätzen

1. **[M]** EmuTOS hat **keine Absturzschleifen-Bremse im Code**. `sh_main` ist eine `do … while`-Schleife ohne Zähler (`aes/gemshlib.c:710-727`); `sh_nextapp` bleibt nach dem Desktop `DESKTOP_APP` (der DESKTOP-Arm ändert ihn nicht, `:600-612`); der Desktop wird also nach **jedem** Ende neu gestartet. Die einzige Bremse ist **konstruktionsbedingt**: der Absturzbericht wartet auf eine Taste (`bios/kprint.c:581-584`), erst dann `kill_program` = `Pterm(-1)` (`bios/panicasm.S:96-99`).
2. **[M]** Der Exitcode des Desktops hat in EmuTOS **genau eine** Wirkung: `if (aes_run_rom_program(deskstart)) wm_new();` (`gemshlib.c:606-609`) — jeder Wert ≠ 0 heißt „abnormal beendet“ → Fensteraufräumen. `sh_ldapp` liefert für den Desktop **immer 0** (`:611`), also **nie** ein `fm_error`.
3. **[M] Korrektur an PROC05:** Ein `Pterm(-1)`-Kind liefert dem Elternprozess **65535**, nicht −1 (`bdos/proc.c:601,616`: `xterm(UWORD rc)`, `run->p_dreg[0] = rc`, `p_dreg` ist `LONG`). Das ist **positiv** → `if (ret < 0)` (`gemshlib.c:681`) ist falsch → `sh_ldapp` gibt 0 zurück → **kein Alert**. `fm_error` kann in `sh_main` nur aus **Ladefehlern** (`xexec` negativ) und `sh_find`→`EFILNF` kommen — und diese Wege propagiert NewTOS **schon** (`launch.rs:86-89`). Der im Ticket PROC05 beschriebene Alert für `Pterm(-1)` ist **kein** EmuTOS-Verhalten.
4. **[M]** NewTOS wirft den Kind-Exitcode auf dem Kernel-Startweg tatsächlich weg: `pterm::terminate(_rc)` ignoriert ihn (`pterm.rs:114`), `finish_terminate` schreibt ihn nur beim `Pexec`-Aufrufer nach `x0` (`exceptions.rs:1537`), der Kernel-Start-Resume stellt nur `elr/sp_el0/spsr` her; `launch.rs:172` liefert `E_OK`. Für den Desktop-Arm heißt das: das EmuTOS-`!= 0 → wm_new()` ist heute **nicht abbildbar**.
5. **[M]** Heute (Desktop auf EL1) endet ein Desktop-Absturz **im Halt**: EL1-Ausnahmen bleiben fatal (`exceptions.rs:301-310`), ebenso ein Kernel-Panic. Eine Schleife gibt es heute nicht.
6. **[M] Das eigentliche Schleifenrisiko von U9 ist ein anderes als bei EmuTOS:** der `panic_handler` der Rust-Laufzeit (`programs/newtos-gem/src/lib.rs:111-124`) macht `Cconws` + `Pterm(-1)` **ohne Taste**. Ein Panic beim Desktop-Start (EmuTOS-C kennt das nicht; dort wäre es eine Ausnahme mit Taste) führt zu: Neustart in Rechenzeit der Ladeschleife, ohne Pause; die Meldung wird sofort von `sh_draw_clear` (`gemshlib.c:719`, `shell_loop.rs:184`) übermalt. Ebenso ein **Ladefehler** des eingebetteten Blobs (`launch.rs:86-89` → sofort zurück).
7. **[M] Blocker bestätigt:** `shell_loop.rs:434` übergibt `&cmd` (128 Byte, nullgefüllt, `:344`) an `run_program_with_tail_rc` → `pexec::load(path, …)` (`launch.rs:81-83`) → `registry::lookup(path_bytes)` (`pexec.rs:269`) vergleicht `entry_name == name` über die **ganze** Scheibe (`registry.rs:102`). `"NEWDESK" != "NEWDESK\0…\0"` → **kein Treffer, FAT-Pfad → `EFILNF`**. Über `svc` funktioniert es (`read_kernel_cstr`/`read_user_cstr` liefern die Länge ohne NUL, `exceptions.rs:1790-1803`). Fix = NUL-begrenzter Vergleich (§4).
8. **[M]** T10: der Fehler liegt in der **Bewaffnungsbedingung** des Injektors (`measurement-…/apply_injector.py`: `RUN.is_null()` → „nur während ein EL0-Programm läuft“; `a78_patch2.py:12-16` wählt das Skript beim ersten Tick). Mit EL0-Desktop sind Desktop, Accessories und TeraDesk **alle** EL0 — die RUN-basierte Wahl wird endgültig bedeutungslos. Tragfähig ist nur ein **kernelseitiges Ereignis mit Programmidentität** (§3).
9. **[M]** `observe_desktop_gem_call` (Schlüssel `Space::Kernel`, `shell_loop.rs:88-94`) muss in U9 auf „Slot des vom DESKTOP-Arm gestarteten Prozesses“ umgestellt werden; der Slot ist heute **nirgends nach außen sichtbar** (`launch.rs` verschluckt `child.slot`). Eine winzige Produktänderung (`launch::SHELL_CHILD_SLOT`) trägt Orakel **und** Injektor-Bewaffnung.
10. **[?]** Offen bleiben (nicht ermittelbar ohne Lauf): Stackbedarf des Desktops, Startlatenz auf der Pi, ob die Absturzaufforderung auf echter Pi 4 funktioniert (ARCH03 0c: „Echte Pi: nicht gefahren“), `render_tree_app` mit LP64-Desktopbaum auf Pixelgleichheit.

## 1. D6 — Absturzpolitik

### 1.1 Was EmuTOS tut (alles [M])

**Normales Ende.** `deskmain` liefert `rc = TRUE` nach `cnx_put(); app_save(FALSE)` (`desk/deskmain.c:2152-2157`), `deskstart` macht `Pterm(0)` (`desk/deskstart.S:53-59`: `restart: jsr _deskmain; tst.w d0; jeq restart; clr.w -(sp); trap #1`). Das Rückgabe-`FALSE` (*Read .INF file*) startet `deskmain` im selben Prozess neu (`:2149`).

**Abnormales Ende.** Der Desktop ist ein ROM-Programm im User-Modus. Jede CPU-Ausnahme läuft über `any_vec` (`bios/vectors.S:225-280`: Register sichern, `lea panic_stack,sp; jmp _dopanic`) → `dopanic` (`bios/kprint.c:302`): Bericht auf dem Schirm, `eat pending keys` (`:581-582`), `*** Press any key to continue ***` + **`bconin2()`** (`:583-584`), dann `kill_program()` (`:594`) = `move.w #-1; move.w #0x4C; trap #1` (`bios/panicasm.S:96-99`). „*we are still running with the PD of the failing program, so calling Pterm() now should clean up and return control to the caller*“ (`kprint.c:588-593`). `xterm(UWORD rc)` (`bdos/proc.c:601`) legt `rc` **zero-extended** als `p_dreg[0]` (LONG) des Elternprozesses ab (`:616`) → `dos_exec` liefert **0x0000FFFF = 65535**.

Ein anderes Abnormal-Ende des Desktops gibt es im EmuTOS-Quelltext nicht: `deskstart.S` kennt nur `Pterm(0)`.

**Wiederaufnahme.** Zurück in `sh_ldapp`:

```c
if (psh->sh_nextapp == DESKTOP_APP) {            // gemshlib.c:600
    sh_show("");  p_nameit(rlr, fname);  p_setappdir(rlr, D.s_cmd);
    if (aes_run_rom_program(deskstart)) {        // :606  -> 65535 nach Absturz
        wm_new();                                // :609  "terminated abnormally"
    }
    return 0;                                    // :611  IMMER 0
}
```

`sh_main` (`:710-727`): `sh_chdef`, `sh_chgrf`, `wm_init`, `ratinit`, `sh_draw(D.s_cmd, TRUE)` (Schirm löschen), `if (rc && !IS_BIOS_ERROR(rc)) fm_error(...)` (`:722-723`; `rc == 0` → nichts), `rc = sh_ldapp(psh)`, `while (doexec != SHW_SHUTDOWN && !gl_changerez)`. **`sh_nextapp` wird im DESKTOP-Arm nie verändert** → nächster Durchlauf = wieder Desktop.

**Schleifenbremse im Code: keine.** Kein Zähler, kein Zeitfenster, keine Unterscheidung „zum n-ten Mal“ in `gemshlib.c`, `geminit.c`, `gemstart.S` (`aes_restart` `gemstart.S:86-124` ist der `gl_changerez`-Pfad, nicht der Absturzpfad). Die einzige reale Verlangsamung ist die Taste in `dopanic`. Ein Desktop, der beim Start mit Ausnahme stirbt, startet also **einmal je Tastendruck** neu — ohne Tastatur (oder bei `bconin2` ohne Quelle) hängt die Maschine im Bericht (`kprint.c:584`), schleift nicht.
(Zusätzlich [A]: `cnx_put/app_save` laufen nur im Normalpfad, `deskmain.c:2152-2157`; ein Absturz überschreibt `EMUDESK.INF` also nicht — eine kaputte INF, die den Absturz auslöst, bleibt im Neustart bestehen.)

**Nicht-Desktop-Programme** (zum Vergleich): `ret = dos_exec(PE_LOADGO, …)` (`:645`); `if (ret < 0) return ret; else return 0;` (`:681-684`). `WORD rc` in `sh_main` (`:694`), `fm_error(-rc-31)` nur für Werte, die `IS_BIOS_ERROR` nicht erfasst (`include/gemerror.h:64`: `n < E_OK && n > EINVFN`, also −1…−31 **ohne** Alert). Ein `Pterm(n)`-Kind liefert 0…65535, nie negativ → nie Alert (§2).

### 1.3 Vorschlag D6 (Entscheidung des Anwenders)

**Grundsatz:** EmuTOS folgen, wo EmuTOS etwas tut; die Lücken, die nur NewTOS hat ((b), (c)), mit der **kleinsten** NewTOS-eigenen Maßnahme schließen und als solche markieren (`// NEWTOS:`).

**D6-1 (EmuTOS-konform, Pflicht):** DESKTOP-Arm nach EmuTOS-Muster, mit Exitcode (setzt PROC05-Teil voraus, §2):

```
rc = launch(NEWDESK)                      // PROC05: Kind-Exitcode, 0..65535, oder Ladefehler < 0
DESKTOP_ACTIVE-Reste aufräumen
if rc != 0 { wm_new() }                   // gemshlib.c:606-609, jeder Wert != 0
return 0                                  // gemshlib.c:611  -- nie fm_error fuer den Desktop
```

`sh_nextapp` bleibt `DESKTOP_APP` → der Desktop startet neu (wie EmuTOS). Kein `fm_error`, keine Sonderbehandlung von 65535.

**D6-2 (NewTOS-eigen, schließt (b)): Panic des Desktops verhält sich wie eine Ausnahme.** Der `panic_handler` der Laufzeit wartet — nur für Programme, die es verlangen — nach der Meldung auf eine Taste, bevor er `Pterm(-1)` macht: `Cconws(msg)`, `Cconws("*** Press any key to continue ***")`, `Cconin()`, dann `Pterm(PANIC_EXIT)`. Technisch: Feature `panic-wait-key` in `newtos-gem` (Standard **aus**, damit `hello-gem`/`panic-test` und alle Messläufe unverändert bleiben), vom `NEWDESK`-Binärcrate eingeschaltet. Begründung: Ein Rust-Panic ist das Gegenstück zu EmuTOS' Ausnahme (`dopanic` + Taste); die Taste war EmuTOS' einzige Bremse. **[A]** `Cconin` aus dem Panic-Handler: Reentranz in einem GEMDOS-Aufruf, der selbst in der Ursache stecken kann (Panic im Allokator) — der Handler hat schon heute `PANICKING` als Wiedereintrittsschutz (`lib.rs:113`) und braucht keinen Heap (`FixedBuf`). **[?]** Verhalten von `Cconin` auf der Pi, wenn die Tastatur nicht initialisiert ist, ungemessen.

**D6-3 (NewTOS-eigen, schließt (c)/(d)): Ladefehler wird nicht wiederholt.** Liefert der Start des Desktops einen **Ladefehler** (`rc < 0` aus `launch`, d. h. das Programm hat nie gelaufen), startet der DESKTOP-Arm **nicht erneut**, sondern nimmt den bestehenden Laufzeit-Ausweichweg derselben Funktion: `report_no_desktop()` + `run_console_arm()` (`shell_loop.rs:357-364,522-530`, EmuTOS' alternatives Haupt-UI `endrom.c:28-35`), mit Meldung auf Seriell **und** Bildschirm. Während D5 lebt, ist die Rückfallstufe stattdessen der Kernel-Desktop (§1.4). Das ist die einzige Stelle, an der ein harter „nicht wiederholen“-Entscheid ohne Zähler möglich ist, denn es gibt keinen legitimen Grund, einen nicht ladbaren Blob ein zweites Mal zu laden.

**D6-4 (optional, NewTOS-eigen): Schleifenwächter für Abstürze nach dem Laden.** Bremse für das, was D6-2 nicht fängt (Hang im Bericht gibt es nicht; es bleibt: Ausnahmen mit Taste, die jemand reflexhaft drückt; ein Desktop, der sofort nach dem Start per `Pterm(-1)` selbst endet). Entwurf:

* Zustand in `sh_ldapp`: `quick_aborts: u8`, `desk_start_tick: u32` (`hz_200`, `tos_api::bios::tick`).
* Ein Lauf zählt als **schneller Abbruch**, wenn `rc != 0` **und** `hz_200 - desk_start_tick < 6000` (30 s). Jeder andere Lauf (lang, oder `rc == 0`) setzt den Zähler auf 0.
* `quick_aborts >= 3` → wie D6-3 (Rückfallstufe + Meldung), Zähler zurück auf 0 erst nach einem Lauf, der nicht schnell abbricht.
* Konstanten `N = 3`, `T = 30 s` sind Vorschlagswerte **ohne Quelle** und benannt als `// NEWTOS:`; ohne Messung (**[?]**) nicht mehr behaupten.
* Wirkung auf legitime Fälle: *Read .INF file* bleibt im Prozess (`deskmain`-Schleife, `lib.rs:268`), `Pterm(0)` zählt nie. Ein Anwender, der den Desktop absichtlich stirbt (z. B. `Pterm` mit Fehler) gibt es nicht.

**Empfehlung:** D6-1 + D6-2 + D6-3 als Pflichtumfang von U9; D6-4 **nicht** in U9, solange die Pi-Abnahme manuell ist und der Anwender am Gerät sitzt (die Taste in D6-2 bremst). D6-4 nachziehen, wenn der Desktop je unbeaufsichtigt hochfahren soll. Das ist ein Kostenpunkt (Zustand + Test), kein EmuTOS-Verhalten.

### 1.4 Zusammenspiel mit D5 (Rückfallschalter)

* **Form (Vorschlag):** Boot-Argument `desk=kernel` in `cmdline.txt`, gelesen wie `input=aes` / `emmc=compat` (`kernel/src/bootargs.rs`, Vorbild „fallback switch“-Konstanten). **Runtime**, nicht Cargo-Feature: auf der Pi genügt ein Editieren der `cmdline.txt` statt eines zweiten Kernelabbilds; derselbe Kern kann A/B fahren (nützlich für G2-Orakel: beide Desktops im selben Abbild, §5 Review). Standard: **EL0-`NEWDESK`** (sonst testet die Pi-Abnahme nichts); `desk=kernel` = alter Weg `desktop::reset(); desktop::run()` (`shell_loop.rs:377-380`) inklusive `lib.rs:606`.
* **Preis:** Der Kernel linkt in U9 die Bibliothek `desktop` **und** bettet das `NEWDESK`-Blob ein (zwei Instanzen derselben Quelle, ein Quelltext, D1). Das ist die ausdrückliche Absicht von D5; die Gruppen C/D der Probe (`Review §3.2` Fußnoten 1/2) bleiben bis U10 bestehen.
* **Automatischer Rückfall (Vorschlag, optional):** D6-3 (und D6-4) nehmen **solange D5 lebt** den Kernel-Desktop statt EmuCON. Vorteil: Ein Pi-Fehlstart braucht keine Kartenänderung, der Anwender hat einen Desktop und kann den Fehler am Bildschirm beschreiben. Nachteil: kleiner Zusatzpfad, der in U10 wieder verschwindet (dann EmuCON). Ich empfehle ihn **mitzunehmen**, weil die Alternative bei einem Fehlstart ohne Tastatur-/Karteneingriff eine tote Pi ist.
* **Nach U10:** `desk=kernel` und der automatische Rückfall entfallen; D6-3 behält die Rückfallstufe EmuCON.

## 2. PROC05 — Exitcode im Shell-Start

### 2.1 EmuTOS-Weg (alles [M])

1. `dos_exec` ist ein Wrapper um `Pexec` aus dem Supervisormodus (`aes/gemstart.S:169-250`).
2. **Rückgabewert von `Pexec`:**
   * Kind läuft und endet mit `Pterm(rc)` / `Pterm0`: `xterm(UWORD rc)` (`bdos/proc.c:601`) → `run->p_dreg[0] = rc` (`:616`; `p_dreg` ist `LONG`, `include/bdosdefs.h:93`) → Elternteil sieht **`rc` als 0…65535** (zero-extended).
   * Kind kommt nicht zum Laufen: negative `xexec`-Codes (`bdos/proc.c`): `EFILNF` (`:230-231`), die Fehler aus `xopen` (`:264-267`), `kpgmhdrld`/`kpgmld` (`:275-279,336-343`), `ENSMEM` (`:286-300`).
3. `sh_ldapp`, NORMAL/AUTORUN-Arm: `ret = dos_exec(PE_LOADGO, …)` (`gemshlib.c:645`) → `if (ret < 0) return ret; else return 0;` (`:681-684`). `sh_find` ohne Treffer: `set_default_desktop(psh); return EFILNF;` (`:687-688`).
4. `sh_main`: `if (rc && !IS_BIOS_ERROR(rc)) fm_error(-rc-31);` (`:722-723`).
5. `fm_error(n)` (`aes/gemfmlib.c:436-472`, `n > 63` → nichts): `n ∈ {2,3,18}` → `AL18ERR`, `4` → `AL04ERR`, `5` → `AL05ERR`, `15` → `AL15ERR`, `8/10/11` → `AL08ERR`, sonst `ALXXERR` („TOS error #n“).

**Welche Werte lösen `fm_error` aus** (`rc < 0`, `rc ∉ −1…−31`, `n = −rc−31 ≤ 63`, `gemerror.h:41-59`):

| `rc` | Name | `fm_error(n)` | Alert |
|---|---|---:|---|
| −33 | `EFILNF` | 2 | `AL18ERR` (nicht gefunden) |
| −34 | `EPTHNF` | 3 | `AL18ERR` |
| −35 | `ENHNDL` | 4 | `AL04ERR` |
| −36 | `EACCDN` | 5 | `AL05ERR` |
| −39 | `ENSMEM` | 8 | `AL08ERR` |
| −46 | `EDRIVE` | 15 | `AL15ERR` |
| −66 | `EPLFMT` | 35 | `ALXXERR` „TOS error #35“ |
| −1 … −31 | BIOS-Fehler | — | **kein** Alert (`IS_BIOS_ERROR`) |
| ≥ 0 (auch 65535, `Pterm(-1)`) | normaler/abgeschossener Exit | — | **kein** Alert |

**Folge:** `Pterm(-1)` (Absturz oder Rust-Panic) erzeugt in EmuTOS **keinen** Alert. Das Ticket PROC05 („Bei NewTOS bleibt z. B. `Pterm(-1)` … still `rc=0`“) setzt voraus, dass EmuTOS hier einen Alert macht — das tut es nicht. **Das Ticket ist an dieser Stelle zu korrigieren.**

### 2.2 NewTOS-Ist ([M])

* Ladefehler: **schon korrekt** — `launch.rs:84-89` gibt `e.errno()` zurück (`PexecError::errno`: `EFILNF`, `EPLFMT`, `ENSMEM`, `pexec.rs:121-145`), `sh_ldapp` gibt `ret` zurück wenn `< 0` (`shell_loop.rs:460-464`), `sh_main` zeigt `fm_error` (`:190-192`, `tos_api::aes::form::fm_error` ist die EmuTOS-Tabelle, `form.rs:831-861`).
* `sh_find`→`EFILNF`: korrekt (`shell_loop.rs:410-415`).
* Kind-Exitcode: **fehlt**. `launch.rs:172 → E_OK` für jedes Programm, das `Pterm` erreicht. Der Wert existiert beim Pterm-Handler (`rc`, `exceptions.rs:1271-1275`) wird aber im Kernel-Start-Resume nicht übergeben (`finish_terminate`: Pexec-Aufrufer-Zweig schreibt `gpr[0] = rc` `:1537`, der Kernel-Start-Zweig stellt nur `elr/sp_el0/spsr` her, Kommentar `:1500-1517`).

### 2.3 Spezifikationstext-Vorschlag (für `docs/api/aes/shell-loop.md` §8 / PROC05)

> **`sh_ldapp` — Exitcode des Kindes.** `launch::run_program_with_tail_rc` liefert den GEMDOS-Wert von `dos_exec(PE_LOADGO, …)`:
> (1) Ladefehler: der negative `PexecError::errno`-Code (unverändert);
> (2) Kind lief: dessen Exitcode als **UWORD, zero-extended in eine nicht negative Zahl 0…65535** (`bdos/proc.c:601,616`). Ein Kind, das mit `Pterm(-1)` endet (Absturz, Panic), liefert **65535**, nicht −1.
> `sh_ldapp` NORMAL/AUTORUN-Arm: `rc < 0 → rc`, sonst `0` (`gemshlib.c:681-684`) — ein Kind-Exitcode löst **nie** einen Alert aus.
> DESKTOP-Arm: `if (rc != 0) wm_new();` — jeder von 0 verschiedene Wert, auch ein Ladefehler (`gemshlib.c:606-609`); Rückgabe an `sh_main` immer `0` (`:611`).
> Die Serienzeile `[shell] sh_ldapp: '<cmd>' exited with rc=N` zeigt den **echten** Wert (bisher stets 0; `docs/sdk/06-image-and-testing.md:266`, `docs/api/desktop/_hw-test-checklist.md:532` nennen `rc=0` für den Normalfall — bleibt gültig, ein sauberes Kind liefert 0).

**Vertrag vs. Interna** (`docs/COMPATIBILITY.md`): Die Zero-Extension des Exitcodes ist **Vertrag** (Programme sehen sie via `Pexec`, schon umgesetzt `exceptions.rs:1271`). *Wie* der Kernelstart den Wert zurückbekommt (z. B. ein `static`/Slot-Feld, das `finish_terminate` vor `release_slot` beschreibt) ist **intern**.

### 2.4 Umsetzungsskizze (für den Developer, kein Code)

* `finish_terminate` kennt `rc` bereits als Parameter (`exceptions.rs:1458`). Im Zweig „weder `pexec_caller` noch `full`“ (= Kernelstart, `:1500-1517`) `rc` an einer Stelle ablegen, die `launch.rs` nach dem Resume liest — vor `release_slot` (`:1562`), der die Slot-Atomics nullt. Ablageort ist Entwurfsentscheidung; Bedingung: ein pro Kernelstart gültiger Wert (es läuft immer nur ein kernelgestartetes Kind gleichzeitig; Verschachtelung `sh_ldapp`→`Pexec`-Kinder läuft über die `Pexec`-Aufrufer-Zweige).
* `launch.rs:172` gibt `Ok(rc)` zurück; `run_program_with_tail` (`:54`: `== E_OK`) und `run_auto_folder` (`:324`) behalten ihre Bedeutung nur, wenn die bool-API „gelaufen“ meint — Auswirkung prüfen: `run_program_with_tail` würde bei `Pterm(n≠0)` `false` liefern. **[A]** Besser: `run_program_with_tail` auf „Kind lief“ (`rc >= 0`) umstellen.
* `sh_ldapp` NORMAL-Arm bleibt (`ret < 0 → ret`). DESKTOP-Arm: `if rc != 0 { wm_new() }`.

### 2.5 Ist PROC05 Voraussetzung für U9?

* **Funktional nein:** Ein Desktop, der normal endet, läuft auch ohne Exitcode (der aktuelle EL1-Weg tut es).
* **Für D6 ja:** D6-1 (`rc != 0 → wm_new()`) und die Unterscheidung „Absturz“ in D6-4 brauchen den Wert. Ohne ihn fehlt nur `wm_new()` nach Absturz — **[A]** und das ist beim heutigen Stand teils schon abgedeckt: `release_client` markiert die Fenster des toten Clients zur Beseitigung (`tos-api/src/aes/mod.rs:963-982`, `mark_for_sweep` → `sweep_dead_clients` im nächsten Dispatch) und `wm_init()` läuft am Schleifenkopf (`shell_loop.rs:182`). Der sichtbare Unterschied ist **[?]** nicht gemessen (Schirmzustand zwischen Absturz und Neustart).

2. **Orakel** (`observe_desktop_gem_call`, siehe §3.4) benutzt dasselbe Datum.
3. **Injektor (Scratch):** Bewaffnung = „`SHELL_CHILD_SLOT` ist belegt **und** der Name des Kindes (der Pfad, den der Scratch-Anker in `launch.rs` sieht) beginnt mit `NEWDESK`“ → `SCRIPT_DESK`; sonst `SCRIPT_TERA`. ### 3.4 Desktop-up-Orakel für EL0 (U8b-Punkt 4)

Heute (`shell_loop.rs:88-123`): `DESKTOP_ACTIVE && space == Kernel && x0 == 200`, `control` über `args.space.get_u64/get_u16`; `appl_init` (Opcode 10) schärft, das nächste `evnt_multi` (25) druckt `[desk] desktop up ({} drives)`.

U9-Schlüssel (**Vorschlag**): `DESKTOP_ACTIVE && running_slot() == launch::shell_child_slot() && x0 == 200`. `running_slot()` ist die Slot-Ableitung aus `RUN` (`sched.rs:176-181`), von `launch.rs:141` (`set_current`) gesetzt; Accessories haben andere Slots, also kein falscher Treffer. Randpunkte:

* **Lesezugriff:** für `Space::User` gehen `get_u64/get_u16` durch `uaccess` (`ldtr`) mit den Rechten des Prozesses; ein Fehler würde ein anstehendes `FaultRecord` erzeugen, das der Aufruf-Schwanz als Absturz des Desktops behandelt (`exceptions.rs:1400-1442`, `uaccess_fault_tail`) — das Orakel dürfte den Desktop also **nicht** wegen eines schlechten Zeigers töten, den nur es liest. Zwei Wege: (a) `control` erst **nach** dem AES-Dispatch aus dem dort schon geprüften Aufrufblock ablesen (`post_dispatch`-Haken, wie `dbg_qedtrace`), (b) `uaccess` ohne Fehlervermerk. Empfehlung (a). **[A]** Der Zeiger ist praktisch immer gültig (der Desktop schreibt ihn selbst in sein Static); das Risiko ist niedrig, aber der Pfad „Orakel verändert Prozessschicksal“ gehört vermieden.
* **ABI-Breite:** `current_abi()` ist LP64 für das Rust-Programm; Zeile `:100-103` deckt beide.
* **Beibehalten:** den Zeilentext und den Anker `kprintln!(\n "[desk] desktop up ({} drives)",` **byte-gleich** lassen, sonst scheitern alle U8a/U8b-Scratch-Injektoren (`inj-*.py` asserten diesen Anker).
* **Einmal je `deskmain`-Lauf:** *Read .INF file* bleibt im selben Prozess und ruft `appl_init` erneut → wird wieder gemeldet (wie heute).
* **Fallback-Desktop (D5):** die Bedingung muss beide Formen kennen: `(space == Kernel && DESKTOP_ACTIVE_KERNEL) || (running_slot() == shell_child_slot() && DESKTOP_ACTIVE_EL0)` — oder eine gemeinsame Flagge `DESKTOP_ACTIVE` plus die Fallunterscheidung am Schlüssel.

## 4. Registry-Blocker

**Befund [M]:** Wie in §0.7. Zusätzlich: `register()` dokumentiert, dass Namen **byte-genau** inklusive etwaiger NULs verglichen werden (`registry.rs:58-62`: „Trailing NULs in the supplied slice **are** part of the name“). `lookup()` bekommt über `svc` Namen ohne NUL, vom Kernelstart den 128-Byte-Puffer. Die beiden bisherigen Registrierer (`selftest_pexec.rs:239`, `selftest_pexec_d4d5.rs:140`) registrieren `b"C"` und rufen über `svc` auf. Der FAT-Zweig kürzt am NUL schon (`pexec.rs:272-273`) — der Registry-Zweig davor nicht: Asymmetrie derselben Funktion.

**EmuTOS-Namensregeln für ROM-Programme [M]:** **Keine.** ROM-Programme werden nicht über einen Namen gefunden: `aes_run_rom_program(PRG_ENTRY *entry)` (`gemshlib.c:570-580`) erzeugt eine Basepage mit `Pexec(PE_BASEPAGEFLAGS, PF_STANDARD, "", NULL)`, setzt `pd->p_tbase = entry` und startet mit `dos_exec(PE_GOTHENFREE, …)`. `D.s_cmd = "EMUDESK"` (aus `set_default_desktop`, `:582-589`, und `sh_chdef` `:551-564`) dient nur Anzeige und `p_nameit`/`p_setappdir`. Die Registry ist eine reine NewTOS-Konstruktion (`// NEWTOS:`, `embedded.rs:23`), der Name ein **Internum** (`aes/shell.rs:66-80`: „reference, not contract“, `DEF_DESKTOP = b"NEWDESK"`).
Für **Dateinamen** gleicht EmuTOS Groß/Klein nicht an der Registry, sondern in `xsfirst`/`ixsfirst`: `toupper` (`bdos/fsdir.c:748,783,814,833,1832`) → GEMDOS-Dateinamen sind case-insensitiv.

**Fix-Spezifikation:**

* `registry::lookup(name)` kürzt `name` am ersten NUL (`name[..position(0).unwrap_or(len)]`) und vergleicht dann mit dem Eintragsnamen. Einträge, die selbst ein NUL enthalten, passen dann nie (bisher dokumentiert als möglich, aber von keinem Aufrufer benutzt, siehe oben) — die `register`-Doku (`registry.rs:58-62`) muss mitgeändert werden („the name ends at the first NUL on both sides“). Alternativ `register` kürzt ebenfalls (symmetrisch), dann bleibt die Doku sinngemäß.
* Der Fix gehört **in `lookup`**, nicht in `shell_loop`/`launch`: sonst bleibt `Pexec(path)` mit einer vom Aufrufer nicht gekürzten Scheibe falsch (z. B. `accs.rs:210` `acc.path` — **[?]** nicht geprüft, ob dort ein NUL-gepolsterter Puffer übergeben wird).
* **Groß/Klein: nicht angleichen** (Empfehlung). Heutiges Verhalten bleibt (exakt), kleinster Eingriff; der einzige Erzeuger des Namens ist die Konstante `DEF_DESKTOP`. Wer Case-Insensitivität will (Analogie zu `fsdir.c:748`), muss wissen, dass dann `Pexec("newdesk")` aus einem EL0-Programm die eingebettete Registry statt einer gleichnamigen Datei im aktuellen Verzeichnis trifft — bei Namen ohne Laufwerk/Erweiterung hat das keine Wirkung auf die Kartennutzung, aber es *ist* eine Verhaltensänderung.
* **Wichtig im Zusammenspiel mit D3 (`#Z` kann anderen Desktop laden):** ein `#Z`-Eintrag `C:\NEWDESK.NAP` hat Laufwerk/Erweiterung, trifft die Registry nie → die Karte bleibt überschreibend, die Registry-Form `NEWDESK` bleibt der eingebetteten Desktopform vorbehalten.

**Tests:**
1. Host (`registry.rs` / `tos-api/tests`): `register(b"NEWDESK", BLOB)`; `lookup(b"NEWDESK")` → Treffer; `lookup(<"NEWDESK" + 121×NUL, 128 B>)` → Treffer; `lookup(b"NEWDESK2")` → keiner; `lookup(b"NEWDES")` → keiner; `lookup(b"NEWDESK\0X")` → Treffer (Name endet am NUL); `lookup(b"")` → keiner; `lookup(b"newdesk")` → keiner (bei exakter Variante).
2. Host: bestehender Selftest-Name `b"C"` weiter.
3. QEMU: DESKTOP-Arm mit eingebettetem Blob startet (Logzeile `[launch] EL0: slot …`, kein `[launch] load failed`).

### 5.1 Stack — reichen 64 KiB?

* **EL1-Ist [M]:** Kernelstack 64 KiB mit 4-KiB-Schutzseite (`link-rpi4.ld:92-99`). **[?]** *Auf welchem Stack* der EL1-Desktop tatsächlich läuft (SP_EL0 im `EL1t`-Betrieb? Boot-Stack `lib.rs:199`?), habe ich nicht verfolgt — das entscheidet, ob die Messung unten den richtigen Bereich lackiert.

### 5.3 Scheduler-/Park-Sonderfälle, die *desktop-spezifisch* sind

**[M]** `KERNEL_PARKED`/`park_kernel_frame` (`sched.rs:167-211`, `exceptions.rs:982-1060`) dienen „NewTOS's built-in desktop **and the boot path**“. `sleep()` (`sched.rs:510-560`): der Zweig `cur < MAX_PROCESSES` (EL0-Prozess mit Slot) ist unabhängig vom Park und ist derselbe, den TeraDesk/QED seit Monaten auf der Pi fahren (Review §0.4). ### 5.6 Weitere U9-Beobachtungen
