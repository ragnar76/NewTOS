2. DESK19 -- confirmed and built
--------------------------------
The premise checks out line for line. `fun_win2win` (`deskfun.c:942-1001`)
resolves the drop target with `i_find` and, `if (pda->a_aicon >= 0)`
(`:962`) -- "dropping file on to an application" -- builds the command line
with `build_selected_path` (`:903-928`) and calls
`do_aopen(pda, TRUE, dst_ob, pdw->w_pnode.p_spec, pdf->f_name, destpath)`
(`:967`), then **returns**: nothing is copied. `build_selected_path` takes the
FIRST selected file and copies either `pn->p_spec`+name or the bare name,
`#if CONF_WITH_DESKTOP_CONFIG if (G.g_fullpath)` (`:915-925`).
`CONF_WITH_DESKTOP_CONFIG` and `CONF_WITH_DESKTOP_SHORTCUTS` (which gates
`do_aopen`'s `if (tail)` arm, `desksupp.c:968-977`) both default to 1
(`include/config.h:1774-1784`), i.e. both are on in our Falcon030/TOS4 profile.

6. The one shape that is ours, not EmuTOS's
--------------------------------------------
`fun_win2win`'s branch ends in `exit_desktop = do_aopen(...)`, i.e. EmuTOS
leaves the desktop process and the AES shell loads the child. NewTOS launches
NESTED (AES gap G1, `main::launch_native`), so `do_aopen_drop` returns `false`
and the desktop is already back when it does. That is the same deviation the
double-click and document-open paths carry, not a new one.

Two answers `do_aopen` does not have, because NewTOS's loader takes native
AArch64 ELF only (ADR-018): a `.PRG`-family target gets the existing "m68k
emulator is not available yet" alert, and a target whose name no native
extension claims gets "This file is not a native NewTOS program". The second
is reachable exactly the way EmuTOS's own quirk is: an installed
application's `ANODE` carries `a_aicon = IG_APPL` **and** its document
wildcard, and `app_afind_by_name` tests `a_pdata` first (`deskapp.c:1450-
1454`), so a document of that type answers `a_aicon >= 0` too -- EmuTOS would
`pro_run` the document. Not driven interactively.


7. One `[EXC]` in 7 runs of the SAME launch -- pre-existing, not DESK19
------------------------------------------------------------------------
The first of the re-driven d19-full runs faulted right after the launch:

    [launch] EL0: slot 0 entry 0x1000
    [EXC] synchronous (non-SVC) exception (Instruction Abort (lower EL)):
          ESR=0x000000008200000e ELR=0xffff0000000c6988 SPSR=0x0000000000000000
    [EXC] FAR=0xffff0000000c6988

Six further runs of the identical script on an identical card copy
(serial/d19-full-serial.log + d19-full-repeat1..4-serial.log, plus the two
earlier passes) are clean, so it is intermittent at roughly 1 in 7.

`ELR`/`FAR` symbolise to
`kernel::arch::aarch64::user_entry::enter_el0_with_resume_capture + 0x6c`,
i.e. the instruction right after the `eret` inside its asm block. EL0 was
executing a KERNEL VA -- which is what happens when an IRQ lands between
`msr elr_el1, {entry}` and `eret` (`kernel/src/arch/aarch64/user_entry.rs:
209-216`): the IRQ entry overwrites `ELR_EL1`/`SPSR_EL1` with the interrupted
EL1 state, and the following `eret` therefore drops to EL0 at that kernel PC,
which faults with a level-2 permission fault (ESR IFSC = 0x0e). Neither
`enter_el0_with_resume_capture` nor its caller `kernel/src/launch.rs:122`
masks IRQs across that window.

That window belongs to EVERY caller of the helper -- the double-click launch,
the AUTO launch, `Pexec`, and eight selftests -- and predates DESK19, which
only adds one more call site. Not fixed here (out of scope, and an arch file);
reported as a new ticket. The screendumps and logs in this directory are from
runs that did not hit it.
