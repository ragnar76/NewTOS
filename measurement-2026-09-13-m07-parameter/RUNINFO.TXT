M07 -- the refusal guard now decides per PARAMETER, and the two arms it was
wrongly locking out really run on both machines.  Taken 2026-09-13.
MEASUREMENT ONLY: this directory states what ran and what came back.

WHAT WAS WRONG
  tosdump/core/cases.c judged a case by its OPCODE.  For six opcodes there is
  no such judgement to make, because the same opcode is a poll or a hang, a
  read of the dumper's own buffer or a write through 0xDEADDEAD, depending on
  one WORD of int_in or on whether the addr_in column named a buffer.  So the
  guard was wrong in both directions at once:

  TOO COARSE -- refused, though one arm is guaranteed safe:
    evnt_multi (25).  MU_TIMER with a zero MT_LOCOUNT/MT_HICOUNT sets `what`
      at gemevlib.c:216-220, BEFORE the `if (what == 0)` block that arms the
      events and calls mwait (:232-262).  It is the one call to evnt_multi
      that is guaranteed to return, and it was exactly the one missing.
    form_error (53).  n > 63 returns FALSE before fm_show (gemfmlib.c:440-441).

  TOO LEAKY -- issuable, though the parameter can be fatal:
    scrp_read (80)   strcpy(pscrap, D.g_scrap), gemsclib.c:40-45: a WRITE of
                     up to 114 bytes through addr_in[0].
    scrp_write (81)  strcpy(D.g_scrap, pscrap), :57-62: an unbounded READ.
    form_keybd (55)  find_obj walks the tree as an OBJECT array bounded only
                     by LASTOB (gemfmlib.c:135-148), reached for
                     RETURN/ENTER/ARROW_UP/TAB/ARROW_DOWN (:167-190).
    objc_delete (41) ob_delete tests `obj == ROOT` and nothing else
                     (gemoblib.c:1154-1157); obj < 0 reads tree[-1].ob_next
                     below the tree base and then WRITES through get_par.

  THE LIVED CASE, and why this is not pedantry: the first draft of the r4
  table contained objc_delete(-1).  NewTOS answers 0 for obj < 0
  (tos-api/src/aes/object.rs) and would have come through clean; the TT would
  have died.  Caught by hand before the run, not by the guard.

WHAT CHANGED
  A second question -- "with THESE values?" -- is now answered per line, next
  to the round-2 window guard and in the same function
  (aes_line_parameter_refusal, core/cases.c).  It runs for preludes exactly
  as for cases.

  IN THE LOADER, NOT ON THE MACHINE, and that is checked rather than assumed:
  every quantity it reads -- the flags, the timer count, the error number, the
  character, the object index, the plants -- is a column of the line.  Nothing
  needs a measured value, so nothing needs a machine.  M06 split the refusal
  at the seam "decidable from the table" / "needs the machine"; M07 lands
  entirely on the loader side of it, which is what the M06 report predicted
  for these two arms.

  What opens: evnt_multi with MU_TIMER and a zero count (and a planted
  MME_PBUFF when MU_MESAG is among the flags); form_error with n > 63; and
  scrp_read/scrp_write/form_keybd WITH a planted buffer.
  What closes: those three without a plant, form_keybd with a navigating key
  (a planted string buffer is not an OBJECT tree, so the plant does not make
  that arm safe), objc_delete with any object but ROOT, and evnt_multi in
  every other shape -- mask 0 most sharply of all, because mwait(0) tests
  `!(0 & p_evflg)`, sets WAITIN and dsptch()es with nothing that can ever
  wake it (gemasync.c:117-125).

  The shape rule that makes it total: where the guard reads an int_in WORD,
  the case must state it AND declare IN_LEN past it.  xif's int_in is a LOCAL
  array copied into only as far as min(IN_LEN, I_SIZE) (gemsuper.c:428-438),
  so a WORD outside IN_LEN is uninitialised stack, not the number the table
  wrote.
