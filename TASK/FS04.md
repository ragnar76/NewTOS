# FS04 — Kopieren ueber eine Partitionsgrenze friert das System sekundenlang ein

Status: **OFFEN** · Prioritaet: **P2** · Typ: Belegter Defekt / Laufzeit — Pi-Runde 2026-09-25

Abhaengigkeiten: —

## Sachverhalt

Auf der echten Pi 4: eine **kleine Textdatei** von einer Partition auf eine
andere kopieren laesst das System **mehrere Sekunden** stehen, danach ist die
Datei drueben. Die Dateigroesse rechtfertigt das nicht.

Dass die Groesse **egal** ist, ist der eigentliche Hinweis: die Wartezeit
skaliert mit etwas anderem — der **Partition**, nicht der Nutzlast.

## Verdacht, als Eingabe formuliert, nicht als Diagnose

**`alloc_cluster` durchsucht die FAT jedes Mal von vorn**
(`tos-api/src/bdos/fs/fat.rs:248-270`): Schleife ueber **alle**
FAT-Sektoren ab `fatrec`, bis ein freier Eintrag gefunden ist. Auf einer
500-MB-FAT16-Partition sind das je nach Clustergroesse einige hundert
Sektoren — und zwar **pro angefordertem Cluster**.

Dahinter liegt ein Sektor-Zwischenspeicher mit **16 Plaetzen**
(`tos-api/src/bdos/fs/cache.rs:18`). Ein Durchlauf ueber mehrere hundert
Sektoren verdraengt sich also **selbst**: jeder Suchlauf liest praktisch alles
erneut von der Karte. Je voller die Zielpartition, desto weiter laeuft die
Suche, bevor sie faendig wird — und desto laenger steht das System.

Zweiter Kandidat, unabhaengig zu pruefen: `count_free_clusters`
(`fat.rs:392`) laeuft ebenfalls ueber die ganze FAT und haengt heute an
`Dfree` (`drive.rs:82`). Wenn irgendetwas im Kopier- oder Neuaufbauweg `Dfree`
ruft, kommt derselbe Durchlauf noch einmal obendrauf.

**Wiederspruch nebenbei, der zu klaeren ist:** der Modulkopf von `fat.rs:13`
behauptet *„no cache yet (Phase 09 D2) — each access reads through the block
device"*, waehrend `cache.rs` existiert und benutzt wird. Eine der beiden
Aussagen ist veraltet.

## Warum P2

„Nichts darf haengen" ist die Vorgabe fuer den Oktober-Termin. Ein System, das
beim Kopieren einer Textdatei sekundenlang steht, sieht auf einer Vorfuehrung
aus wie ein Absturz — und Kopieren ist eine der ersten Handlungen, die jemand
ausprobiert.

## Arbeit

**Erst messen, dann bauen.** Die entscheidende Zahl ist, wie viele
Sektorlesungen ein Kopiervorgang ausloest und wie sie sich verteilen: ein
Zaehler im Blockgeraet, ein Lauf in QEMU raspi4b ueber eine Partitionsgrenze,
und die Verteilung auf `alloc_cluster` / `count_free_clusters` / den Rest. Das
entscheidet zwischen den Kandidaten, statt den erstbesten zu behandeln.

Danach die Abhilfe an der Stelle, die die Messung zeigt. Naheliegend, aber
**nicht** vorweggenommen: ein Suchzeiger („weiter, wo zuletzt gefunden") wie
ihn TOS und FAT-Treiber ueblicherweise fuehren, und/oder ein Cache, der einen
FAT-Durchlauf ueberhaupt halten kann.

Abnahme: dieselbe Geste, gemessene Zeit vorher/nachher, und die Sektorzahl als
Beleg, dass die Ursache getroffen wurde und nicht nur das Symptom.
