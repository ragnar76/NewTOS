# A75 — appl_read blockiert nie, appl_write liefert 0 auf voller Queue: zwei Vertragsunterschiede

Status: **OFFEN** · Prioritaet: **P3** · Typ: Konformitaet / Nebenbefund A30

Abhaengigkeiten: —

## Herkunft

Nebenbefunde N3/N4 des A30-Messdesigns (2026-09-19,
`docs/analysis/a30-appl-init-recall-measurement-design-2026-09-19.md` § 6).

## Sachverhalt

- **`appl_read` (11):** EmuTOS wartet auf leerer Queue (`ap_rdwr` →
  `aqueue`/`mwait`, `gemqueue.c:98-124`); NewTOS' `appl_read` kehrt sofort
  zurueck (`tos-api/src/aes/appl.rs:366-369`). Der Dumper-Riegel (`cases.c`,
  11 BLOCKS) beschreibt EmuTOS, nicht uns — die Asymmetrie ist selbst der
  Befund.
- **`appl_write` (12):** EmuTOS blockiert den Sender auf voller Queue
  (> 7 Nachrichten, `gemqueue.c:96-124`) und gibt sonst 1; NewTOS gibt 0
  zurueck (`pd.rs:166-168`).
- Spec `docs/api/aes/application.md:225` erwaehnt weder den sofortigen
  Rueckweg bei `qready` noch den Senderblock.

## Arbeit

Spec zuerst (beide Vertraege mit Zeilen), dann angleichen: `appl_read`
wartet wie `ap_rdwr` (im kooperativen Kern ueber denselben Warteweg wie
`evnt_multi`), `appl_write` auf voller Queue wie EmuTOS — oder, wenn das
im Single-Task-Kern einen Selbst-Deadlock bedeutet, die Abweichung benannt
in `docs/COMPATIBILITY.md`. Hosttest je Fall. Vorher pruefen, ob eine
Zielanwendung (TeraDesk, QED) `appl_read` auf leerer Queue ruft.
