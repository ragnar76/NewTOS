3. THE CAUSE (read from EmuTOS, not inferred from the log)
---------------------------------------------------------------------------
It is NOT (only) the timeout the ticket suspected. The timeout is the
*second* half; the first half is which scheduler primitive the barrier uses.

EmuTOS `wait_for_accs` (aes/geminit.c:599-628) spends each pass in
`all_run()` (:612), and `all_run` (:554-566) is

    for (i = 0; i < num_accs; i++)  dsptch();      /* :559-562 */
    wm_update(BEG_UPDATE); wm_update(END_UPDATE);  /* :564-565 */

`dsptch` (aes/gemasm.S:129-167) jumps to `disp` (aes/gemdisp.c:220-254),
which branches on the CALLER's own state:

    p = rlr;  rlr = p->p_link;                 /* gemdisp.c:225-226 */
    if (p->p_stat & WAITIN)  mwait_act(p);     /* :230  park on nrl */
    else                     disp_act(p);      /* :231             */

and `disp_act` is `p->p_stat &= ~WAITIN; insert_process(p, &rlr);`
(gemdisp.c:74-79) -- straight back onto the ready list. `ap_exit`
(aes/gemaplib.c:251-255) has no `ev_block` between its entry and the call,
so it is in the `else` branch: EmuTOS's barrier is a bounded round-robin
YIELD. It needs nothing but the dispatcher and makes progress on a machine
nobody is touching.

NewTOS was in the other branch. `tos-api/src/aes/acc.rs::wait_for_accs`
called `sched::sleep(sched::wait_input())`, i.e. `mwait_act`: the caller was
taken out of the cooperative run-set with a WAIT_INPUT wake key, and only
`sched::idle_wake_pass` -- a console byte or a pointer-state change -- could
put it back. Headless there is neither. (Interactively a moving mouse hides
it; before ACC02-ACC05 there were no accessories at all, so `all_have` was
vacuously true and the barrier never slept.)

The bound is real too, and is the second half of the fix: EmuTOS's `n` is a
C automatic and its loop never leaves the function, whereas a NewTOS pass
leaves it on every yield and re-enters from the top (the S2 restartable
block). A stack counter would be reset by every yield -- the precaution
against infinite loops would itself become one.

Extracted into the spec as docs/api/aes/accessories.md §3a (new), with
docs/api/aes/application.md `appl_exit (19)` step 3 corrected to match.
Nothing in docs/api/ had said what the "block" is; that omission is why the
wrong primitive looked acceptable.

ACCEPTANCE MET: a headless run in which a program passes through

continues to the desktop afterwards.

The trace is EmuTOS's shape: `mn_cleanup` posts AC_CLOSE and wakes both
accessories, `all_run` dispatches to slot 0 and slot 1, each consumes the
message (setting AP_ACCLOSE) and blocks again, the round-robin comes back to
slot 2 because the waiter never left it, the `fpdnm` walk passes, the call
returns.

7. WHAT THIS DOES NOT ESTABLISH
---------------------------------------------------------------------------
* Nothing was run on real hardware. Everything here is QEMU raspi4b.
* No interactive run: the point was the headless case, so no click, no key
  and no pointer movement was fed to any of these boots.
* The `wm_update(BEG_UPDATE)/(END_UPDATE)` bracket of EmuTOS's `ap_exit`
  (gemaplib.c:253,258) and its trailing `all_run()` (:259) are still absent
  from NewTOS's `appl_exit`. They are a separate divergence, reported, not
  touched here.
* `appl_yield` (AES 17) still returns 1 without dispatching, where EmuTOS
  calls `dsptch()` (gemsuper.c:116-118). The primitive it would need now
  exists; wiring it is a separate change.
