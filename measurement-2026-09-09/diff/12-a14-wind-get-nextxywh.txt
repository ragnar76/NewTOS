5. D-A14-1 -- DER EIGENTLICHE A14-BEFUND: der Cursor ist global
======================================================================

Quelle. w_rnext ist ein Feld der WINDOW-Struktur, aes/gemlib.h:85:

      ORECT *w_rlist;             /* owner rectangle list */
      ORECT *w_rnext;             /* used for search first, search next */

Es gibt also einen Cursor PRO FENSTER. wm_get holt pwin = get_pwin(
w_handle) (gemwmlib.c:1513) und waehlt dann pwin->w_rlist bzw.
pwin->w_rnext (:1559); w_owns schreibt pwin->w_rnext (:1235). Eine
Abfrage auf Fenster B beruehrt den Cursor von Fenster A nicht.

Die Spezifikation sagt dasselbe, richtig und ausdruecklich:
docs/api/aes/window-graphics.md:335-337 -- "`WF_NEXTXYWH` continues from
the saved cursor `pwin->w_rnext`".

Umsetzung. tos-api/src/aes/window.rs:1054-1064 haelt EINEN statischen
RLIST { rects, count, cursor } fuer die gesamte AES. wind_get ruft
compute_rlist(handle) nur im FIRST-Arm (:2000-2002) und danach
rlist_next() (:2003) -- rlist_next nimmt kein Handle entgegen
(:1142-1155). Der Cursor ist damit global und der NEXT-Arm liest das
Handle ueberhaupt nicht.

Gefahren, Hostlauf, beide Profile, identisches Ergebnis:

  FIRST(1)  ->  1, 31, 63, 296, 17     (TOP-Stueck von Fenster 1)
  FIRST(2)  ->  1, 61, 103, 176, 114   (setzt den globalen Cursor um)
  NEXT(1)   ->  1, 0, 0, 0, 0          <-- Listenende gemeldet
  NEXT(1)   ->  1, 0, 0, 0, 0
  NEXT(1)   ->  1, 0, 0, 0, 0

  Soll nach EmuTOS: NEXT(1) muesste (31,80,29,162) liefern, dann
  (262,80,65,162), dann (31,242,296,15).

  Und in der anderen Richtung:
  FIRST(1) -> (31,63,296,17); NEXT(1) -> (31,240,296,17);
  FIRST(2) -> (61,103,176,114); NEXT(2) -> (0,0,0,0);
  NEXT(1)  -> (0,0,0,0)                <-- Fenster 1 hat noch zwei Stuecke

Schadensbild. Ein Programm, das nach dem im Soll beschriebenen Idiom
(window-graphics.md:342-346) zwei Fenster in einem Durchgang neu zeichnet
-- oder dessen Schleife von einem Accessory unterbrochen wird, das
seinerseits WF_FIRSTXYWH stellt -- bekommt fuer das erste Fenster nach dem
ersten Stueck sofort das Listenende gemeldet und laesst drei Viertel
seiner Arbeitsflaeche stehen. Genau der Befund, den ein GEM-Programm als
"Fenster bleibt halb leer" zeigt.

Verdikt: CONFIRMED, quellen- UND spezifikationswidrig. Gefahren wurde er
im Hostlauf; eine MESSUNG existiert dafuer nicht, weil die eingefrorene
Tabelle keinen verschachtelten Fall enthaelt. Er ist damit quellenbelegt,
nicht messbelegt.

6. D-A14-2 -- NEXT prueft sein Handle nicht
======================================================================

Dieselbe Codestelle, andere Wirkung. Weil rlist_next() kein Handle nimmt,
antwortet NEXT auf jedes Handle aus der Liste des zuletzt per FIRST
abgefragten Fensters -- auch auf ein Handle, das es nicht gibt.

Gefahren, Hostlauf, beide Profile, nach FIRST(1) und zwei NEXT(1):

  NEXT(7)   -> 1, 31, 80, 29, 160     Handle 7 existiert nicht
  NEXT(-1)  -> 1, 260, 80, 67, 160    negatives Handle
  NEXT(99)  -> 1, 0, 0, 0, 0          jenseits der Tabelle
  FIRST(7)  -> 1, 0, 0, 0, 0          (der schon aus A13 bekannte Fall)

  Soll: get_pwin liefert fuer ein negatives, ein zu grosses oder ein nicht
  benutztes Handle NULL (gemwmlib.c:1395-1401); WF_NEXTXYWH faellt in den
  default-Arm der ersten switch und wm_get liefert FALSE (:1521-1523).
  int_out[0] muss also 0 sein und int_out[1..4] unberuehrt bleiben.

Das ist die NEXT-Haelfte von D-A13-1 (A13 hat sie fuer FIRST belegt); der
Ort ist derselbe, window.rs:1999-2010 steht vor jeder Handlepruefung. Neu
gegenueber A13 ist, dass NEXT sein Handle auch dann nicht liest, wenn es
gueltig ist -- das ist D-A14-1.

Verdikt: CONFIRMED, quellenwidrig. Nicht messbelegt (kein TT-Record fuer
ungueltige Handles in dieser Tabelle).
