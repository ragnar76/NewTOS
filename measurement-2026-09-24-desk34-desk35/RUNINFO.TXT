measurement-2026-09-24-desk34-desk35
===================================
DESK34 (a folder opened inside a window navigates in place)
DESK35 (a launched GEM application owns the whole screen)

Base: branch desk-rebuild, HEAD a84b0ba. This batch's changes are UNCOMMITTED
in the shared tree (kernel/src/desk/main.rs, kernel/src/shell_loop.rs — full
diff in method/desk34-desk35.diff). Nothing flashed, nothing ejected, no real
Pi run, nothing committed. No `git checkout/restore/clean/stash/reset` was run
on the shared tree.

Machine: QEMU `-M raspi4b`, 640x480, `-display none`, serial to file, QMP

tables (SCRIPT_DESK plus the empty SCRIPT_TERA the script selector needs).

POINTER PARK: (600, 240) — clear of the desktop icons and of the menu bar, as
in the DESK03..DESK06, DESK19/DESK20 and DESK22 runs.

Both tickets are FIXES, not withdrawals: the "before" runs below are the
defect, the "after" runs are the acceptance.

1. Geometry and fixtures, measured
---------------------------------------------------------------------------
  The card is tools/make-sd-image.sh plus three files in the ROOT, written by
  method/seed.sh:

    C:\GEMWIN.NAP   method/gemwin.c, built with sdk/build.sh (6880 bytes)
    C:\QED.NAP      a copy of C:\Apps\QED\QED.NAP     (501592 bytes)
    C:\qed.rsc      a copy of C:\Apps\QED\qed.rsc      (41378 bytes)

  Why QED is opened in the root and not where make-sd-image.sh installs it:
  the click coordinates are baked into the action list, and in the "before"
  build every folder step opens a NEW window (that is DESK34) — so navigating
  C:\ -> Apps -> QED would put the program icon somewhere else in the two
  builds and the before/after pictures would no longer be the same gesture.
  QED finds its resource through `sh_find`'s app-directory step, so the .rsc
  travels with it.

  Why GEMWIN.NAP exists at all (the ticket allows "add the smallest .NAP that
  paints something and says so"): DESK35 needs a GEM program that (a) paints
  ONLY its own rectangles and (b) terminates by itself.
    * DUMPVDI.NAP fails (a): every case starts with `v_clrwk`
      (tosdump/core/runner.c:82), which clears the WHOLE screen — it would
      wipe the leftover desktop windows in the "before" build too, and the two
      pictures would match for the wrong reason.
    * QED.NAP fails (b): it is interactive and ends through its own menu.
  gemwin.c does appl_init / wind_create / wind_open(160,120,320,200) / v_bar +
  v_gtext inside its OWN work area / evnt_timer(6000) / close + appl_exit.
  Deliberately NO v_clrwk. It lives in method/, not in the product.

  method/d-probe.actions + method/d-probe2.actions, serial/d-probe*-serial.log.
  d-probe2 opens the C:\ window twice, so the item grid of the cascaded second
  window is dumped as well:

    [probe] desk obj 9 idx 0 box (0,19) 76x40 -> click (38,35)   C: drive icon
    [probe] win slot 0 handle 1 spec C:\*.*
    [probe]   obj 17 'SUB'        box (477,87)  76x40 -> click (515,103)
    [probe]   obj 25 'GEMWIN.NAP' box (141,171) 76x40 -> click (179,187)
    [probe]   obj 37 'QED.NAP'    box (141,255) 76x40 -> click (179,271)
    [probe] win slot 1 handle 2 spec C:\*.*
    [probe]   obj 56 'GEMWIN.NAP' box (165,195) 76x40 -> click (203,211)
    [probe]   obj 68 'QED.NAP'    box (165,279) 76x40 -> click (203,295)

  and from the same run's AES trace, window 1's work rect:

    [aes] op 104 in=(1,4,…) out=(1,49,85,520,335)     wind_get(1, WF_WXYWH)

  Window 1 is the slot-0 fallback rectangle (48,43,544,400) and window 2 the
  slot-1 one, cascaded by (+24,+24) — which is why every window-2 item sits 24
  px right and 24 px down of its window-1 twin. The C: drive icon at (37,42)
  is LEFT of window 1's left edge (48), so it stays clickable with windows
  open; that is the point all the earlier rounds used too.


2. DESK34 — a folder opened inside a window   (d34-*, serial/d34-*-serial.log)
---------------------------------------------------------------------------
  method/d34.actions, one run per build, both acceptance cases in each:
  double-click the C: drive icon, then the SUB folder at (515,103) inside the
  window it opened, then the drive icon again.

  before (HEAD)                      after
  --------------------------------   --------------------------------------
  d34-before-B-win1.png              d34-after-B-win1.png
    one window, title C:\              identical

  d34-before-C-folder.png            d34-after-C-folder.png
    a SECOND window, title C:\SUB\,    the SAME frame, title C:\SUB\, the
    the C:\ one still behind it        three items of C:\SUB\ in it

  d34-before-D-drive.png             d34-after-D-drive.png
    a THIRD window (C:\)               a SECOND window (C:\)

  and the serial probe says it in the desktop's own bookkeeping:

    before  [probe] win slot 0 handle 1 spec C:\*.*
            [probe] win slot 1 handle 2 spec C:\SUB\*.*      <- a new node
    after   [probe] win slot 0 handle 1 spec C:\SUB\*.*      <- the same node
            (slot 1 / handle 2 appears only after the drive icon)

  That is EmuTOS `do_fopen`'s `else` arm, `pn_close(&pw->w_pnode)` +
  `do_diropen(pw, FALSE, …)` (desksupp.c:1151-1156), and its `do_dopen`
  neighbour (`:1041-1069`) unchanged for the drive.

  NOT driven here: Alt+double-click (EmuTOS' third new-window case,
  `(keystate & MODE_SCA) == MODE_ALT`, `:1132-1134`). The IKBD injector feeds
  mouse packets and raw key bytes; it sets no modifier state that
  `graf_mkstate` reads. Real keyboard — Pi checklist item 59.

---------------------------------------------------------------------------

  double-click GEMWIN.NAP at (203,211) in the top one. The program holds its
  window for 6 s and returns by itself.

  d35-before-D-app.png   BOTH desktop windows, both desktop icons, the trash
                         and the printer still standing; GEMWIN's own window
