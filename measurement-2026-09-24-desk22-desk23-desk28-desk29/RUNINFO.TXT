    C:\AUTO\AUTOCHD.NCP   method/autochdir.c — `Dsetpath("\SUB")`, runs FIRST
    C:\AUTO\CURDIR.NCP    sdk/examples/curdir.c (DESK18) — runs SECOND

  d28-before-A-auto-text.png / d28-after-A-auto-text.png are the same two
  lines on the \AUTO\ text screen. `PROOF: C:\AUTO` is not printed in either
  run and cannot be: EmuTOS' `autoexec` issues no `Dsetdrv` and no `Dsetpath`
  (bios/bios.c:685-733), so the AUTO child's directory is the BIOS process's
  own — `Dsetdrv(bootdev)` (bios/bios.c:827) and, for a drive that was never
  `Dsetpath`ed, the root DND `ckdrv` installs (bdos/fsdrive.c:119-131). The
  ticket's "\AUTO\" reading is withdrawn; what the change fixes is the leak
  from one AUTO program into the next, which our global drive/directory
  stand-in had and EmuTOS's per-process copy does not.

  d28-*-B-desktop.png: the desktop comes up normally after the AUTO phase in
  both builds. 0 [EXC]/[PANIC] in both logs.

4. DESK23 — the two frame corners               (method/pixels.py, all dumps)
---------------------------------------------------------------------------
  WITHDRAWN. The premise was "wind_open leaves two corner pixels unwritten and
  the repaint writes them white". Neither path writes them, and there are four
  of them, not two.

  Window 1 is (48,43,544,400). EmuTOS draws the W_BOX border with
  `gr_box(t.g_x,t.g_y,t.g_w,t.g_h,1)` and then, for SHADOWED, after
  `gr_inside(&t,th)` with th=1 (aes/gemoblib.c:889-900):

      bb_fill(… t.g_x,          t.g_y+t.g_h+th, t.g_w+th, 2*th)   bottom band
      bb_fill(… t.g_x+t.g_w+th, t.g_y,          2*th,     t.g_h+3*th) right band

  which for this window is border x 48..591 / y 43..442, bottom band
  x 49..591 / y 443..444, right band x 592..593 / y 44..444. Four pixels are
  in none of them: (592,43), (593,43), (48,443), (48,444) — the band starts
  one pixel in on each side, on purpose. Our `draw_frame`/`draw_shadow`
  (tos-api/src/aes/window.rs) computes the identical rectangles.

  Nor does the desktop paint them: all four lie inside the window's WS_TRUE
  (= its rectangle grown by DROP_SHADOW_SIZE, aes/gemwmlib.c:253-261, here
  48..593 x 43..444), and the rectangle lists are built from WS_TRUE
  (`newrect`, aes/gemwrect.c:190), so `w_drawdesk`'s `do_walk(DESKWH, …)`
  (gemwmlib.c:340-359) has no rectangle that contains them. Nothing writes
  them. Their colour is whatever was on the screen when the window opened.

  method/pixels.py over screendumps/ shows exactly that:

    d29-B-win1 … d29-F-win2-back   (592,43)=white (593,43)=green
                                   (48,443)=white (48,444)=green
    d22-*-B-window                 same
    d22-*-C-program                all four white   (the console cleared the
                                                     screen — see the whole
                                                     picture: every pixel is)
    d22-*-D-after                  all four white   (the repaint did not touch
                                                     them)

  white/green alternating is the desktop's own background dither, which is
  why the DESK06 diff saw two differing pixels and not four: at (592,43) and
  (48,443) the pattern is white anyway, so they match the console's white.

  The d29 run is the control the other way round: five window opens, toppings
  and full frame repaints in a row, never a screen clear — and the four pixels
  stay on the desktop pattern from beginning to end. So the difference DESK23
  measured belongs to the screen that was underneath, not to either draw path.
  Nothing changed.


5. DESK29 — a selection and a window change     (d29-*, serial/d29-serial.log)
---------------------------------------------------------------------------
  WITHDRAWN. EmuTOS clears unconditionally, in two places:

    desk/deskmain.c:1282-1292  case WM_TOPPED: desk_clear(G.g_cwin); …
    desk/deskmain.c:957-959    wh = wind_find(mx,my);
                               if (wh != G.g_cwin) desk_clear_all();

  and `G.g_cwin` only becomes the new window afterwards, in `desk_verify`
  (desksupp.c:196). Our `main::top_msg` and `main::hndl_button` are both
  verbatim that. A selection therefore cannot survive a window change on
  EmuTOS either, and `do_aopen`'s second position does not need one: it takes
  the directory of `win_ontop()` (desksupp.c:878, 898-901), so the case is
  reached with an icon that is NOT in the top window — a desktop icon, or a
  drag's destination — not with a stale selection in another window.

  The run shows the current behaviour:
    d29-C-win2.png       two windows on C:\, window 2 on top
    d29-D-selected.png   README.TXT selected in window 2; its info line reads
                         "64 bytes used in 1 selected items."
    d29-E-after-top.png  after one click in window 1's uncovered work area:
                         window 1 on top
    d29-F-win2-back.png  window 2 topped again — README.TXT is NOT selected,
                         info line "424568 bytes used in 28 items."

  and the AES trace names the path, in EmuTOS' order (between MARK D_SELECTED
  and MARK E_AFTER_TOP in serial/d29-serial.log):

    [aes] op 105 in=(2,3,…)    wind_set(2, WF_INFO)  ← desk_clear's win_sinfo
    [aes] op 105 in=(1,10,…)   wind_set(1, WF_TOP)   ← top_msg's wind_set

  i.e. `desk_clear(G.g_cwin)` on the old window first, `WF_TOP` on the new one
  second. Nothing changed.
