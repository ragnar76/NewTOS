A29 -- the AES process descriptor survives the end of a program.
Measurement, 2026-09-14.
MEASUREMENT ONLY: this directory states what ran and what came back.


THE EFFECT, MEASURED FIRST (acceptance point 1)
  The desktop runs in the kernel boot context and gets AES id 1
  (tos-api/src/aes/appl.rs, current_pid with a null basepage).  The first
  program it launches lands in GEMDOS slot 0, whose AES id is slot+1 = 1
  (aes::pid_of_slot).  Desktop and first child therefore share ONE AES process
  descriptor -- which is EmuTOS-faithful: sh_ldapp renames the one rlr for each
  successive program (references/emutos/aes/gemshlib.c:633-636).

  Both of NewTOS' end-of-program paths destroyed that shared descriptor:
      appl_exit()          -> pd::close          -> *slot = Aespd::EMPTY
      close_client_if_open -> pd::close_if_open  -> *slot = Aespd::EMPTY
  After that pd::by_pid(1) is None.  Measured consequences, through the LP64
  dispatcher (tos-api/tests/aes_app_return_descriptor.rs):

      appl_write(1, msg)                       0 instead of 1
      the desktop's own wind_open -> appl_read 0, buffer [0,0,0,0,0,0,0,0]
                                               instead of 1 + the WM_REDRAW

  What that costs the user, read off the posting sites rather than guessed
  (every one of these goes through pd::post_msg / post_words -> by_pid):
      menu selection      aes/event.rs menu_intercept posts MN_SELECTED and
                          returns true; the caller then dequeues it through the
                          regular MU_MESAG arm.  No descriptor = the drop-down
                          opens, the item click is consumed, nothing happens.
      window frame        aes/window.rs intercept() posts WM_CLOSED / WM_FULLED
                          / WM_MOVED / WM_SIZED / WM_ARROWED / WM_?SLID /
                          WM_TOPPED.  The AES draws the rubber box for a drag
                          and then drops the message, so the window snaps back;
                          the closer does nothing; a click on a lower window
                          does not top it.
      window content      aes/window.rs send_redraw posts WM_REDRAW on open /
                          close / move / size / top.  Dropped.
  Silent at the moment of return -- desk::main::desktop_resume repaints the
  whole screen directly (redraw::redraw_desktop -> win_shwall_nocursor), so the
  picture comes back intact.  Visibly wrong at the next interaction.

  REACHABILITY.  Only through the desktop's own launch path
  (desk/main.rs run_gem_app: desktop_relinquish -> launch -> desktop_resume),
  because that path does NOT call appl_init again.  The #Z-autorun path does
  not have the defect: there the program runs BEFORE the desktop, and
  shell_loop sh_ldapp's DESKTOP arm then calls desk::run(), whose first act is
  appl_init() (desk/mod.rs) -- a fresh descriptor.  EmuTOS does the same thing
  for the same reason: sh_main re-enters deskstart after every normal
  application (gemshlib.c:710-727), so its desktop re-registers too.


EMUTOS AT THE SAME BOUNDARY (acceptance point 2)
  Pin references/emutos @ 1a7484aba1bfba23e2c0899e243b6d8177fe41df, read here.

  aes/gemaplib.c:251-261   ap_exit -- wm_update(BEG), mn_cleanup,
                           wait_for_accs(AP_ACCLOSE),
                           "if (rlr->p_qindex) ap_rdwr(MU_MESAG, rlr,
                           rlr->p_qindex, (WORD *)D.g_valstr);",
                           wm_update(END), all_run,
                           "rlr->p_flags &= ~AP_OPEN;"
  aes/gemshlib.c:650-657   sh_ldapp, immediately after dos_exec returns --
                           "if (rlr->p_flags&AP_OPEN) { mn_cleanup();
                             if (rlr->p_qindex) ap_rdwr(MU_MESAG, ...);
                             rlr->p_flags &= ~AP_OPEN; }"
  Neither frees the AESPD.  Neither CAN: the descriptors are fixed entries of
  D.g_int[] / D.g_acc[] addressed by index (aes/gempd.c:32-35, pd_index), and
  fpdnm(NULL,pid) -- what APPL_WRITE resolves its target with
  (aes/gemsuper.c:102-105) -- walks that array with no liveness test at all
  (aes/gempd.c:38-57).  A message addressed to a pid always finds its
  descriptor, before and after appl_exit.
  aes/gemshlib.c:633-636   the shared-descriptor premise: p_nameit(rlr,fname),
                           p_setappdir, rlr->p_flags = 0 -- the SAME rlr is
                           renamed for the next program.  (The p_flags = 0 half
                           is A28 and is NOT touched here.)
  The two NewTOS specs already said all of this and the code deviated from
  them: docs/api/aes/application.md "appl_exit (19)" steps 1-7 and
  docs/api/aes/shell-loop.md "Arm 3" both list the drain and the AP_OPEN clear
  and neither mentions freeing anything.  No spec correction was needed; a
  NewTOS note was added under appl_exit recording what the code used to do.

WHY THE DEFECT ITSELF IS NOT IN ANY OF THESE RUNS -- measured, not assumed
  The only in-tree way to launch a program FROM a running desktop is a
  double-click (desk::main::hndl_button -> launch_native -> run_gem_app) or a
  keyboard equivalent (hndl_kbd).  Both need HID input.  The two emulators
  give one of input and C: storage, never both, and the two logs here say so:
      raspi4b  "[pcie] RC not present (no response at RC_BASE); USB disabled"
               and C: works (25 items listed)          -> storage, no input
      virt     usb-kbd and usb-mouse enumerate, and
               "[desk] desktop up (0 drives)"          -> input, no storage
  So the end-to-end gesture -- open a directory window, double-click an app,
  quit it, then use the menu / close box / drag the window -- is REAL PI 4
  ONLY.  It is listed as such in TASK/A29-STATUS-UNFINISHED.MD.
