WHAT WAS WRONG
  tosdump/core/cases.c refused five opcodes outright, reasoning "TOS 3.06 =
  AES 3.20" (include/config.h:1345-1354).  True of TOS 3.06, and beside the
  point: both machines these dumps are taken on report ap_version 0340, and
  the same ladder makes 0x0340 mean CONF_WITH_3D_OBJECTS &&
  CONF_WITH_MENU_EXTENSION && CONF_WITH_WINDOW_COLOURS &&
  CONF_WITH_GRAF_MOUSE_EXTENSION.  The guard was locking out functions the
  reference ROM measurably HAS.  TASK/M06.md.

WHAT CHANGED
  The question was split at the only line where it can be split.  The LOADER
  -- which runs on the host with no machine in the room -- still answers "is
  this opcode issuable at all" and now also records WHICH capability the
  table needs.  The MACHINE answers "do I have it", once, after appl_init
  (which is what writes ap_version, gemsuper.c:92) and before the first case
  or prelude, in td_aes_cases_version_refusal().  A machine that does not
  have it refuses the WHOLE table by name and runs nothing, so a dump has
  `count` records or there is no dump.  Details: tosdump/core/cases.h, the
  version guard.

  Opened by this: objc_sysvar (48) and menu_popup/attach/istart/settings
  (36-39).  NOT opened: the four CONF_WITH_PCGEM opcodes (appl_yield 17,
  scrp_clear 82, shel_rdef 126, shel_wdef 127) -- that flag is not in the
  ladder, so ap_version cannot settle them and they stay refused.

  NOT A FINDING OF THIS RUN, BUT VISIBLE FROM THE SOURCE: EmuTOS' get arm
  writes *out2 only for LK3DIND, LK3DACT and AD3DVALUE; NewTOS writes
  int_out[2] for every get.  This table declares OUT_LEN 2 for the three
  colour selectors on purpose, because OUT_LEN 3 there would deliver the
  TT's UNINITIALISED xif stack (gemsuper.c:429-432, :444-445) and measure
  the stack rather than the AES.  A table that wants to measure that
  difference needs a different instrument, not a bigger OUT_LEN.

  be run on a freshly started AES and ends with indtxtmove, indcolchange,
  actcolchange and indbutcol changed.  Both runs above boot fresh.
