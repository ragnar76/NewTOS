0. The card, and the scaffolding
---------------------------------
Seeded on top of the standard image (`method/seed.sh`), so a folder copy has
something to collide with:

    C:\DESKT24\FOLD\INNER.TXT   34 bytes, "CHARLIE inside the source folder"
    C:\DESKT24\ONE.TXT           5 bytes
    C:\DESKT24\TWO.TXT           5 bytes
    C:\FOLD\EXIST.TXT           27 bytes, "DELTA already on the root"

So dragging `C:\DESKT24\FOLD` onto the `C:` desktop icon is a folder copy into
`C:\` whose destination folder name is already taken -- EmuTOS's
`output_path()`/`get_new_name()` case.

All dumps go through `tos_api::aes::h02_log` (the a79 serial-only sink) or
`kprintln!`; nothing reaches the framebuffer, so the pictures stay clean.

2. DESK24 -- confirmed and built
--------------------------------
Before (serial/d24-before-serial.log) the drag produces the counting box and
then nothing:

    [d25] dir_op op=Count  icontype="<absent>" src="C:\DESKT24\" n=1
    [d24] CPYDEL root=(160,159,320,180) ... files=1 dirs=1 confirm=true
    [d25] dir_op op=Copy   icontype="<absent>" src="C:\DESKT24\" n=1

-- no `CPALER` line: the old code did `let _ = dos_mkdir(&dst_sub)` and merged
into the existing folder without asking. The card afterwards
(serial/cards.txt, d24-before.img) has `C:\FOLD\{EXIST.TXT, INNER.TXT}`.

After, the same gesture puts EmuTOS's dialog up for the FOLDER, pre-filled
with the destination name in BOTH fields (`deskdir.c:705-709`, unlike the file
case where `CACURRNA` is the source):

    [d24] CPALER ... curr="FOLD" copy="FOLD"        screendumps/d24-merge-d-conflict.png

  * OK on the unchanged name (`ret == 1`, `deskdir.c:770-775`):
        [d24] CPALER answer ob=4 ... copy now "FOLD"
        [d24] output_path(Copy, "C:\FOLD") -> Ok, dst now "C:\FOLD"
    and the card has `C:\FOLD\{EXIST.TXT 27, INNER.TXT 34}` -- merged, as
    EmuTOS merges. `C:\DESKT24\FOLD\INNER.TXT` is untouched.
  * `2` typed into the editable field (`ret == 2`, the loop goes round again
    and `dos_mkdir` succeeds):
        [d24] CPALER answer ob=4 ... copy now "FOLD2"
        [d24] output_path(Copy, "C:\FOLD") -> Ok, dst now "C:\FOLD2"
    and the card has a NEW `C:\FOLD2\INNER.TXT 34` while `C:\FOLD` still holds
    only `EXIST.TXT` -- screendumps/d24-rename-d-typed.png shows the typed
    name in the field, e-renamed.png the result.

Both answers are read out of the card image with method/lsimg.py, not off the
screen (serial/cards.txt).

    with `Yes` / `No` and the default on `No` -- `STDELDIS`, `desk_rsc.c:2499`.

with the wrong argument: EmuTOS calls it inside `rebuild_window`

6. `fsck_msdos` on the two whole-drive wipes -- a PRE-EXISTING finding
-----------------------------------------------------------------------
`fsck_msdos -n` is clean (Phase 1/2/3, rc=0) on eleven of the thirteen images.
The two it is not clean on are `d25-yes.img` and `d25-before.img`, the only two
on which a whole drive was emptied; on both it dies with exit 133 and prints
nothing at all.

It reproduces identically on the HEAD build, so DESK25 did not cause it --
DESK25 only puts a question in front of the same delete. The cause is that
GEMDOS `Fdelete`/`Ddelete` erase the 8.3 entry and leave the preceding
long-filename slots (`attr == 0x0F`) behind; the card carries them because
macOS wrote `.fseventsd`, `.Spotlight-V100` and the `._*` companions with LFN
chains. `ctl-nolfn.img` -- a copy of `d25-yes.img` with exactly those 35 slots
marked erased (`method/lfn_orphan_probe.py --fix`) -- passes Phase 1/2/3 with
rc=0 and 0 files.

Full record and the remaining open question in serial/fsck.txt; the slot dump
in serial/lfn-d25-yes.txt. Reported as a new ticket, not fixed here.
