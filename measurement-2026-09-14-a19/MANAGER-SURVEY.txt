A19 -- which AES manager reads past the IN_LEN / AIN_LEN the caller declared?
============================================================================
2026-09-14.  The question the ticket puts BEFORE the fix, because it decides
whether the defect is latent or active.  Answer up front: **latent**.  Not one
handler in tos-api/src/aes/ reads an int_in word or an addr_in slot past what a
conforming binding declares for its opcode.  The one function that comes close
-- wind_get(WF_COLOR/WF_DCOLOR) -- reads exactly the slot EmuTOS' own wm_get
reads, and the standard binding declares it.

METHOD
  ours       every `pb.intin(N)` / `pb.intin_ptr(N)` / `pb.addrin(N)` in
             tos-api/src/aes/{appl,event,form,fsel,graf,menu,object,resource,
             shell,window}.rs, mechanically extracted.  Every index in the
             tree is a literal -- there is no computed index to miss.
             Helpers are folded into their caller:
               window.rs set_newdesk / wf_str_ptr -> wind_set
               menu.rs   do_chg                   -> menu_text
               fsel.rs   run                      -> fsel_input/fsel_exinput
               graf.rs   set_user_form            -> graf_watchbox
  soll       the count a conforming caller declares, taken from
             (G) references/emutos/desk/gembind.c, EmuTOS' own AES binding --
                 AES_CTRL_CODE(op, nintin, nintout, naddrin), line cited
             (L) sdk/gemlib/gemlib-0.44.0-m68k/a_*.c AES_PARAMS(op,ni,no,na,nao)
                 for the nine opcodes the EmuTOS desktop never calls
             cross-checked against the int_in[] slot macros in
             references/emutos/include/aesdefs.h:161-609 and the crysbind arm
             in references/emutos/aes/gemsuper.c:77-421.
  verdict    OK    = highest index read < declared length
             =MAX  = reads exactly the last declared word (no margin, correct)
             OVER  = reads past the declaration

NOTES
  1  appl_tplay (14) and appl_trecord (15) read NO int_in word although the
     binding declares 2 and 1.  That is an under-read, the opposite defect,
     and it is NOT A19's: it belongs to whatever those two handlers do or do
     not implement.  Out of scope, untouched, reported.
  2  wind_get(WF_COLOR) / wind_get(WF_DCOLOR) read int_in[2] -- the gadget
     number.  EmuTOS does exactly the same: crysbind hands wm_get
     `&WM_IX` = `&int_in[2]` (gemsuper.c:342) and wm_get reads `pinwds[0]`
     for both fields (gemwmlib.c:1568, :1573).  gemlib's binding declares
     IN_LEN 3 for precisely those two fields and 2 for every other
     (a_wind_get.c:336-348), so a conforming caller covers the slot.
     EmuTOS' OWN desktop binding declares 2 unconditionally
     (desk/gembind.c:757) and would therefore read its uninitialised stack --
     an EmuTOS inconsistency, not a NewTOS one, and the desktop never asks
     for either field.  Our kernel/src/desk/mod.rs never asks for them
     either (wind_get_grect/wind_get_top, both IN_LEN 2, fields 4..12 only).
  3  shel_write (121) reads int_in[0..1] and not SH_ISCR = int_in[2] which
     the binding declares.  Again an under-read, out of scope, untouched.

WHAT THE CLAMP CHANGES IN PRACTICE
  Every in-tree caller was checked the same mechanical way and none
  under-declares against what its handler reads:
    kernel/src/desk/mod.rs        24 call sites, all n_int >= the highest
                                  intin[] index they set
    tos-api/tests/*.rs            every `pb.call(op, in_len, ...)`
    tos-api/tests/aes_reference/  331 case/prelude calls across the four
                                  frozen tables
  Three shapes in the frozen tables sit exactly on the boundary and were
  checked case by case:
    * 55 x wind_get with IN_LEN 2 -- none of them asks for field 18 or 19,
      so none reaches int_in[2].
    * case 140 of aes-r2-wind.tsv, "wind_create IN_LEN 1" -- the one measured
      case that deliberately under-declares.  wm_create parks the rectangle in
      WS_FULL and returns only the handle, and the case declares OUT_LEN 1, so
      what the rectangle became is not in the record.  Passes either way; it
      is the reason this ticket's own regression test uses that call shape with
      a recognisable pattern instead.
    * the one Kind::IntIn plant, cases_m05_addrin.rs:102 -- wind_set with
      IN_LEN 6 and a packed pointer at word 2.  At LP64 the pointer occupies
      words 2..5, i.e. exactly the six declared words.  min(6,16) = 6 leaves
      it whole.  Had the table declared 4 (the m68k count) the clamp would
      have cut the pointer in half; it does not.
