measurement-2026-09-24-drag-regression
  Regression pass for DESK36 (commit f85f9c8): the desktop's drag loop was
  rewritten from a single AES `graf_dragbox` (71) call to the desktop's own
  `gr_drgplns`/VDI-workstation loop, and `fun_desk2win` / `fun_desk2desk` /
  `fun_file2desk` / the menu-delete branch were switched from
  `desktop_selected_disks()` to `desktop_selected_sources()`. This directory
  re-drives every DRIVE-PATH drag/delete/copy case that worked before that
  swap, on the CURRENT committed tree, to show it still works.
===========================================================================

Scope: branch desk-rebuild, HEAD d88fa16 (f85f9c8 already committed; d88fa16
is a docs-only commit on top). Tester only -- no product code touched. No
`git checkout/restore/clean/stash/reset` was run on the shared tree. Nothing
flashed, nothing ejected, no real Pi run, nothing committed, nothing pushed.

Machine: QEMU `-M raspi4b`, 640x480, `-display none`, serial to file, QMP
screendumps (`method/run.sh` + `method/qmp_multi.py`, copied from
measurement-2026-09-24-desk37-desk36-desk30/method, the harness that already
builds against this exact committed state). Card: a single fresh
`tools/make-sd-image.sh` image (`method/seed.sh`) plus the DESK13 + DESK19 +
DESK24 fixture folders combined onto it (they do not collide), copied fresh
per run. Interactive runs use the scratch-copy IKBD injector (memory
`desktop-interactive-verification-real-hw`): the scratch tree lives in the
job's own scratchpad, rsynced from the shared tree, never the shared tree
itself.

**Why coordinates differ from the older measurement directories.** The
`C:\` window now holds far more files than when DESK13/19/20/24/25/26 were
first measured (BIG.NCP, LIBTEST.NCP, CLOCKTST.NCP, SETJMPT.NCP, MATHTST.NCP,
COREMARK, ... all added by later, unrelated tickets), so the icon grid
positions of DESKT13/DESKT19/DESKT24/SAME.TXT/README.TXT/CMDLINE.NCP etc. are
different today. Desktop-icon geometry (C: at (38,35), Trash at (38,449),
Printer at (584,449)) and every dialog's geometry (ADCPYDEL, ADCPALER,
STDELDIS, ADDESKCF -- none of their building code was touched by f85f9c8,
confirmed by reading the commit's diff) are unchanged and were reused as
recorded. Every OTHER coordinate below was re-measured fresh against the
CURRENT card with a probe harness (`method/probe1..probe6.actions`,
`method/probe_patch.py`'s `do_wredraw`/desktop-up dump), not carried over
from the old measurement directories, and not guessed.

**A behaviour change found while building the harness, logged and reasoned
through, turned out to be unrelated to this ticket.** Opening a subfolder now
NAVIGATES the current window instead of opening a new small staggered one
(`method/probe2..probe4c` established this; `probe6` confirmed the desktop
DISK icon still opens a genuinely NEW window). That is commit c38408e ("a
folder navigates its window"), already merged before f85f9c8, not part of
this regression's scope. It broke literal reuse of the two-window
`d19-defdir-app`/`d19-defdir-win` gesture from the original DESK19/DESK20
measurement (see §5, "not driven").

3. DESK19 -- dragging a file onto a program, both *Parameter* settings
   (rg-d19full, rg-d19file)
---------------------------------------------------------------------------
Single window (C:\), drag README.TXT onto CMDLINE.NCP -- `fun_win2win`'s
drop-on-an-application branch (`build_selected_path` + `do_aopen_drop`,
unchanged by f85f9c8; only the drag LOOP feeding it is new).

**A methodology trap, found and corrected, not a product bug.** The first
attempt used an injector "mark" step scheduled after the drop as the wait
condition, the same convention the older `.actions` files use, and it never
fired -- both attempts (80 s and 180 s budgets) stalled identically right
after `[launch] returned (program Pterm'd)`. Root cause, read from source
(`kernel/src/desk/main.rs::console_pause_for_key`): after an `.NCP` returns,
the desktop shows "[ Press any key to return to the desktop ]" and blocks in
`Host::console_read_key_blocking`, which polls USB-HID/IKBD DIRECTLY and
does **not** call through the AES-pump anchor the H02 injector's `step()` is
hooked into (confirmed by reading both `console_read_key_blocking` and the
`apply_injector.py` anchor). No scripted "mark" can ever fire while stuck
there -- not a regression, a pre-existing harness ceiling: the ORIGINAL
(pre-DESK36) `measurement-2026-09-23-desk19-desk20/serial/d19-full-serial.log`
ends at the exact same `[launch] returned` line with no further `[h02]`
output, for the identical reason. That measurement's screendump was captured
against the program's own dual-logged `Cconws` text ("CMDLINE: len ... arg"),
not an injector mark. Corrected here to do the same
(`method/run_batch3.sh`, `method/rg-d19file-v3` invocation) -- the wait
marker is the literal program output, which appears in the log the instant
`Cconws` runs, well before the blocking read.

5. Not driven here
---------------------------------------------------------------------------
  * DESK19's *Default dir* pair (`d19-defdir-app`/`d19-defdir-win`, two
    windows, one on top of the other). The original two-window recipe
    (Alt+C, double-click the subfolder to open a SECOND staggered window)
    no longer applies: opening a subfolder now NAVIGATES the current window
    (commit c38408e, already merged before f85f9c8, out of scope for this
    ticket). A working substitute exists -- double-clicking the DESKTOP disk
    icon still opens a genuinely new window even while the first shows a
    subfolder (`method/probe6.actions` confirmed this) -- and a redesigned
    action list was drafted (`method/probe7.actions`) but not run: the
    `Default dir` resolution itself (`do_aopen`'s `pathname` vs. `win_ontop()`
    choice, `desksupp.c:896-905`) was not touched by f85f9c8 (confirmed by
    reading the commit's `main.rs` diff -- only the shortcut prologue and the
    `do_aopen_drop` call sites changed, not `do_aopen` itself), so this is a
    lower-risk gap, not a suspected regression. Flagged for a follow-up
    measurement, not this one.
  * Real Pi 4 (the acceptance gate for anything cache-sensitive or
    interactive-input-dependent): none of this regression pass needed real
    hardware -- every case here is mouse-drag + dialog + FAT16 content, all
    reproducible in QEMU raspi4b with the scripted IKBD injector.
